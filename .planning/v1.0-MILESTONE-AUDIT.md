### ATT-01 — the D-04 retention guarantee is proven only on an unreachable path

This is the finding that matters most, because three separate artifacts attest to a behavior the
code does not have.

`PlanningRepository.refresh()` never throws (D-12). On a failed target check it **overwrites**
`this.snapshot` with `project: null` and resolves normally (`snapshot.ts:61-70`). The server then
runs `derived = buildDerivedViews()` unconditionally (`index.ts:235`), so the last good bundle is
replaced by an empty presentation — server-wide, for every subsequent request, not just the
caller's. The response reports `refreshed: true` and returns the failed read's `readAt`
(`index.ts:236-240`).

The three attestations:

1. `test/server/refresh.test.ts:179` proves retention — for a **rejecting** `refresh()`. That is
   the path D-12 says production never takes.
2. `test/server/refresh.test.ts:165-176` covers the path production **does** take
   (resolve-to-failed-snapshot), asserts `refreshed: true`, and never checks retention — it
   codifies the defect as intended behavior.
3. `04-VERIFICATION.md:134` cites that suite as TGT-08 evidence ("retention ... tested"), and
   `04-UI-REVIEW.md:31` claims "Forced refresh failure retained the original `readAt`" — which
   can only have exercised a throw or a client-side fetch failure, not a resolved failed read.

This also violates plan 04-01's own judgment-tier prohibition: *"the UI never presents a failed
read attempt's time as the age of retained data."* The prohibition was declared
`verification: judgment` precisely so it could not silently pass, and it silently passed.
