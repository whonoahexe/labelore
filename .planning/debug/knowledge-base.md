## loading-state-regression — route-transition top bar never appeared on in-app navigation; page blank ~12s on load
- **Date:** 2026-09-16
- **Error patterns:** no errors in console, loading bar never appears, top bar missing on navigation, skeletons don't appear, sidebar icon delayed, slow page switching, blank page for several seconds, Suspense fallback not rendering, RouteProgress, React.lazy, startTransition, useNavigation idle, NODE_ENV unset, Vite dev middleware served in production
- **Root cause(s):** ENVIRONMENT — the Cloudflare tunnel origin ran `node src/server/index.ts` with `NODE_ENV` unset, so `createApp(source, production = process.env.NODE_ENV === 'production')` was false and Hono served the Vite dev middleware instead of `./dist`; at 150ms RTT that is 55 unbundled round trips and a fully blank page until t=11,792ms (vs 14 requests / t=765ms in prod); **and** CODE — `RouteProgress` was wired only as the `<Suspense fallback>`, but React renders a fallback only when the boundary MOUNTS, and react-router runs navigations inside `startTransition` where React deliberately keeps an already-mounted boundary's children on screen, so the bar could never paint on an in-app navigation (reproduced identically in dev and prod); **and** STRUCTURAL — `app-shell.tsx` gated the drawer trigger behind `{tree.isSuccess ? <SidebarDrawer /> : null}`, making the sidebar icon wait on a 120,265-byte `/api/tree` payload (482ms lag in prod, 564ms in dev)
- **Fix:** Moved the loading signal off the Suspense-mount event onto the lazy factory itself — new `src/web/components/route-chunk-store.ts` counts chunks in flight, `trackRouteChunk` wraps each `React.lazy` factory (increment on entry, decrement in a `finally` so a 404'd chunk cannot strand the bar), and `RouteProgress` reads it via `useSyncExternalStore` rendered by the shell ABOVE the boundary, where it is already committed and free to repaint while the boundary below suspends. Boundary keeps a layout-only `RouteFallback`. Listener notification deferred with `queueMicrotask` (the counter increments during another component's render). Removed the `tree.isSuccess` gate. Added a serve-mode startup banner (`console.warn` on the dev branch). Replaced the source-text contract assertions with 6 behavioural tests driving the store directly.
- **Files changed:** src/web/components/route-chunk-store.ts (new), src/web/components/route-progress.tsx, src/web/components/app-shell.tsx, src/web/app-router.tsx, src/server/index.ts, test/web/route-chunk-store.test.ts (new), test/web/loading-state-contract.test.ts, test/web/shell-contract.test.ts, test/web/build-splitting.test.ts
- **Why not caught:** A gate existed and was green. `test/web/loading-state-contract.test.ts` was written by the same quick task that introduced the bug and **passed on the broken code** — every assertion was source-text pinning with an IMPLICIT oracle (does the file contain `createPortal`, `document.body`, `ROUTE_PROGRESS_DELAY_MS = 150`, `clearTimeout`, the a11y attributes). All of that was true of the broken version: the bar existed, was debounced, portalled and accessible — it simply never received a signal. Typecheck, lint and review could not have caught it either; the broken code is type-correct, lint-clean, and reads as obviously right. The defect lived in an interaction between three libraries (React Suspense semantics × react-router `startTransition` × `React.lazy`), visible in the source text of no single file. RC1 had no gate at all — nothing in startup output, the health endpoint, or the served HTML stated which mode was serving, so a dev-mode process sat behind a public tunnel for 26 hours with zero signal.
- **Recurrence guard:** `test/web/route-chunk-store.test.ts` — 6 behavioural tests driving `trackRouteChunk`/`routeChunkStore` with no DOM and no renderer, mutation-verified (killed 3/6 and 5/6 against two deliberate mutants, one of them the identity wrapper that reproduces the original no-signal defect). The store lives in a plain `.ts` module precisely so it stays drivable without a React renderer — the architectural half of the same guard. Plus: `src/server/index.ts` startup banner pinned by a contract test asserting both branches exist and that the dev branch is a `console.warn`; and comment-stripping in the contract test's identifier counts.

### Transferable lessons

1. **A `<Suspense fallback>` cannot signal an in-app navigation.** It renders only when the boundary MOUNTS. Under `startTransition` (which react-router uses for every navigation) React deliberately keeps an already-mounted boundary's current children on screen instead of swapping in the fallback. A route-loading indicator must therefore be driven from the `React.lazy` factory itself and read by a component rendered **above** the boundary — that component is already committed and free to repaint while the boundary below it suspends. Symptom signature: the indicator works on a hard load but never on a client-side navigation.

2. **`useNavigation()` is not a viable lazy-chunk detector.** Two independent reasons, both verified against react-router 8.3.0 source: (a) `router.js:693` short-circuits `completeNavigation` **before** assigning `updates.navigation = loadingNavigation` whenever no matched route declares a `loader`, `middleware`, or custom `dataStrategy` — so in an `element:`-only route table `navigation.state` never leaves `"idle"`; and (b) even with loaders present, a `React.lazy` chunk download happens in React's render phase via Suspense and is completely invisible to the router's navigation lifecycle, so the router would report idle while the chunk was still in flight. Check the installed version's source before assuming the idiomatic hook applies.

3. **Source-text contract tests have an implicit oracle and pass on broken code.** Asserting that a file *contains* certain identifiers proves the parts exist, never that they are wired together. Here the entire pre-existing suite was green on the defect. Only a behavioural test that drives the unit is a real guard — and **extracting the logic into a plain `.ts` module is what makes it drivable** without a renderer or a DOM. When a test would need JSX/DOM config just to observe a behaviour, that is a signal to extract, not to loosen the tsconfig.

4. **A server that does not announce its serve mode is a silent footgun.** A dev-mode process sat behind a public tunnel for 26 hours with no signal anywhere — not in startup output, not in the health endpoint, not in the served HTML. Startup banners for mode-dependent behaviour are cheap insurance; make the wrong-mode branch a `console.warn` naming both the consequence and the remedy, not an easily-missed `console.log`.

5. **Identifier-counting tests must strip comments first.** A `/\blazy\(/g` count matched 6 real calls plus one prose comment ("Every routed page is lazy()-loaded") and reported 7. Fix the counter, not the comment — rewording prose leaves the same trap for the next person, and the failure mode cuts both ways (prose can make correct code look broken, or a broken implementation look correct).

6. **Suspect an AND-gate when no single cause explains every symptom.** Three independent causes here; fixing any one alone left the others fully intact, and the mode-independent reproduction (bar missing in *both* dev and prod) is what proved the code defect was not merely a side effect of the environment defect. Differential probing across two build modes at a matched RTT was the experiment that separated them.
