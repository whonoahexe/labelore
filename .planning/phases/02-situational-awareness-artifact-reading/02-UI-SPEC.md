## Spacing Scale

**Gap identified (carried forward, unchanged by this revision).** The implementation does **not**
follow a discrete 8-point token scale. It uses fluid, purpose-fit `rem` values throughout
(`0.65rem`, `0.82rem`, `0.85rem`, `1.15rem`, `1.25rem`, `clamp(1.25rem, 3vw, 2rem)`, etc.) chosen
per-component for visual rhythm rather than snapped to a 4px grid. This was a deliberate authoring
choice for a typography-led, editorial layout (Sera style) and is consistent with itself, but it is
**not** the standard GSD 4/8/16/24/32/48/64 contract.

**Retroactive contract (documents actual state; not a redesign):**

| Token | Value | Usage (as implemented) |
|-------|-------|-------------------------|
| xs | ~0.4–0.45rem (6–7px) | Icon-to-label gaps (`.eyebrow`, `.status-chip`, `.text-link`) |
| sm | ~0.65–0.85rem (10–14px) | Compact internal padding (chips, wave-band rows, metadata panels) |
| md | ~1–1.25rem (16–20px) | Default card/panel padding, list-item vertical rhythm |
| lg | `clamp(1.25rem, 3vw, 2rem)` (20–32px) | Section padding on major panels (`.immediate-work`, `.attention-panel`, `.milestone-flow`) |
| xl | `clamp(1.5rem, 4vw, 3.5rem)` | Document canvas padding, page-stack horizontal padding |
| 2xl | `clamp(2rem, 5vw, 4.5rem)` | Page-intro / hero vertical spacing |
| 3xl | `clamp(2rem, 5vw, 5.5rem)` – `7rem` bottom | Page-stack top/bottom padding |

**Exceptions (forward guidance for Phase 3/4 additions to this surface):** New spacing decisions in
later phases on this same visual surface (roadmap, dashboard, artifact reader) should snap to
4px-multiple values (4, 8, 12, 16, 24, 32, 48, 64) wherever a new value is introduced, to begin
converging the surface toward the standard scale — but do **not** retroactively rewrite the passing,
already-shipped Phase 02 CSS as part of this contract capture. Icon-only touch targets (`icon-sm`
button = 2.25rem/36px, `icon` = 2.5rem/40px) are an accepted exception to any 44px minimum, consistent
with a desktop-first local dev tool; no mobile-specific touch-target audit is in scope for Phase 02.

## Structural Nesting Rule (Revision — G-08)

**The complaint was systemic, not a single component.** "Too many blocks inside the blocks, making
it a bunch of nested cards in many pages" is a layout-system defect, not a per-component styling
tweak — so this section states a normative, checkable constraint that applies to every page, not
just the artifact reader where it was measured.

### The rule

**Maximum nesting depth: two boxed layers, anywhere in the app.**

A "boxed layer" is any element carrying a visible `border`, a `background-color` distinct from its
nearest boxed/backgrounded ancestor, or a `box-shadow` — anything that reads visually as "this is a
container." Counting only applies along an **ancestor–descendant** chain (a box nested inside
another box); sibling boxes at the same depth (e.g. three dashboard panels side by side) never count
against each other.

- **Layer 1** — at most one container per content region may establish "this is a distinct object"
  (a panel, a popover, a table's own scroll boundary, a code block).
- **Layer 2** — permitted **only** inside a Layer-1 box, and **only** where the box is doing
  functional work (most commonly: a scroll boundary, e.g. a code block's own edge). A Layer-2 box
  that exists purely for decoration is not allowed.
- **Layer 3 never exists.** A box inside a box inside a box is prohibited on every surface, full
  stop — this is what "flattest" means as a developer decision (see below), and it generalizes
  beyond the artifact page the tester measured it on.

**Checkable test:** walk any DOM path from `#root` to a leaf. Count elements along that single path
whose computed style adds a border, a background-color step, or a box-shadow relative to the nearest
such ancestor above them. That count must never exceed 2.

### Applied retroactively (developer decision: Option A, flattest)

- **`.document-canvas`** (the artifact page's outer document container) **loses its border and
  offset hard-shadow entirely.** The page background *is* the document background; page-stack
  padding supplies the margin that the card border used to provide. `.document-canvas` is no longer
  a boxed layer at all.
- **`.plan-section`** (the rendering shell for PLAN pseudo-XML wrappers — both recognized sections
  and the new generic fallback below) **loses its box entirely** — no border, no
  `background-color`. It keeps its existing label typography plus a single hairline top rule
  (`border-top: 1px solid var(--border)`), which does not count as a boxed layer (a single rule on
  one edge, not an enclosing border). `.plan-section` is no longer a boxed layer.
- **`pre` code blocks keep exactly one border.** This is now the only Layer-1 box that survives
  inside the (now unboxed) document canvas and (now unboxed) plan section — and it exists because it
  is the functional scroll-boundary edge required by the Code Block Overflow rule below, not
  decoration. Nesting depth at a code block inside a plan section inside the document canvas is now
  **1**, not 4.
- **Inline `code` (`:not(pre) > code`)** drops its border. It becomes a plain, subtle
  background-tint span — `background: color-mix(in oklch, var(--secondary) 70%, transparent)`, no
  border — so it reads as an inline text treatment, not a chip. It is not a boxed layer.

### What this does NOT change

Panels elsewhere in the app that are not nested inside another box — `.immediate-work`,
`.attention-panel`, `.metadata-panel`, `.wave-band`, `.coverage-matrix`, the reference-preview
popover — remain Layer-1 boxed cards exactly as before; none of them were the source of the
complaint, and none of them sit inside another box. `.immediate-work` keeps its existing offset
hard-edge box-shadow accent; it is the one deliberate "stacked card" treatment left in the app.
The rule these must still obey going forward: if a Layer-1 panel contains a sub-list or sub-group,
that sub-group renders as plain rows with hairline dividers between rows, never as its own nested
box — this is the guardrail that stops the depth-4 pattern from recurring on a page the tester has
not yet UAT'd.

the surface) rather than a discrete 3–4-size scale. This is intentional editorial/display styling
(large hero numerals, uppercase mono labels, long-form reading body) but diverges from the standard
GSD "declare exactly 3–4 sizes" contract.

## Artifact Rendering — Unknown PLAN Sections (Revision — G-01 / G-11)

**This is the highest-priority fix in this revision.** The prior implementation gates section
rendering on `RECOGNIZED_TAGS`, a fixed whitelist (`objective`, `context`, `decision`, `tasks`,
`task`, `name`, `files`, `action`, `behavior`, `implementation`, `verify`, `done`, `what-built`,
`how-to-verify`, `resume-signal`, `verification`, `success_criteria`, `output`). Any tag outside
that list is skipped by the segmenter entirely, so its opening and closing tags — and everything
between them — falls through to ordinary markdown rendering as literal text (`</execution_context>`,
`<read_first>`, `<scope_note>`), and because the wrapper text sits inline in the markdown source,
it also disrupts the surrounding block structure — this is why `<read_first>` blocks lose their list
formatting (G-11): the raw tag text breaks markdown's blank-line/indentation contract for list
recognition.

**This contradicts the project's core constraint that unknown artifact input must degrade, not
break** (`.claude/CLAUDE.md` — "GSD's artifact set evolves, so unknown files must degrade rather
than break"). A whitelist is a guarantee of recurrence: every new tag GSD's PLAN grammar introduces
in the future reproduces this exact defect. The fix specified here is therefore a rule change, not a
whitelist addition.

### The rule

**Section segmentation is unconditional. Bespoke treatment is conditional.**

1. Every syntactically well-formed wrapper — an open tag matching `<([A-Za-z][\w-]*)...>` paired
   with its matching `</tag>`, outside fenced code — **is always segmented** into a labelled
   section. There is no tag name for which the correct behavior is "fall through to raw text."
   Whether a tag is on the existing recognized list determines *only* whether it gets bespoke
   presentation (badges from `type`/`gate`/`tdd` attributes, special ordering, a hand-authored
   label) — never whether it becomes a section at all.
2. **Recognized tags** (the existing list above) keep their current bespoke rendering exactly as
   implemented — task badges, checkpoint semantics, etc. Nothing here changes for them.
3. **Every other syntactically valid tag** renders through one **generic fallback treatment**:
   the same visual shell now specified for all plan sections (label + hairline top rule, no box —
   see Structural Nesting Rule), with the label **auto-derived from the tag name**: convert
   `snake_case` or `kebab-case` to Title Case (`execution_context` → "Execution Context",
   `read_first` → "Read First", `scope_note` → "Scope Note"). No visual distinction in weight,
   color, or emphasis from a recognized section's label — same `.plan-section-label` typography.
4. **The section's inner text is extracted identically for recognized and unrecognized tags** —
   using the segmenter's existing `contentStart`/`contentEnd` span, exactly as already implemented
   for recognized tags. That extracted text is handed to the normal markdown pipeline
   (`remark-parse` → `remark-gfm` → …) exactly as a recognized section's body already is. This is
   the fix for G-11: because the wrapper's raw tag characters are no longer left sitting in the
   markdown source (they're consumed by the segmenter either way), the markdown *inside* the
   wrapper — including lists — parses normally regardless of whether the tag name was recognized.
5. **Malformed tags** (unclosed, mismatched open/close) keep the existing `plan-segment-warning`
   treatment unchanged — this rule only changes the outcome for syntactically *valid* tags that
   were previously unrecognized, not for genuinely broken markup.

### Implementation shape (for the executor)

`RECOGNIZED_TAGS` stops being the gate for "does this tag produce a segment" — it becomes only the
gate for "does this segment get the tag-specific bespoke renderer, or the generic one." Concretely:
the segmenter (`segmentPlanBody`) accepts **any** tag name matching the grammar pattern into the
open/close stack machinery it already has (currently gated by `if (!RECOGNIZED_TAGS.has(tag))
continue;` — that early-return is the bug). The **rendering layer**, not the segmenter, branches on
`RECOGNIZED_TAGS` membership to decide bespoke-vs-generic presentation.

### Acceptance test

Render `/home/cinedise/studio-portal/.planning/phases/01-portal-owned-identity-sessions/01-01-PLAN.md`
(the exact file the UAT flagged) and confirm: no literal `<tag>` or `</tag>` text is visible
anywhere in the rendered output, `<read_first>` renders its enclosed list as a real `<ul>`/`<li>`
structure (not a run-on paragraph), and every section — recognized or not — carries a labelled
header.

## Code Block Overflow (Revision — G-10)

**No fenced code content is ever silently clipped.** The prior implementation declared
`overflow-x: auto` on `pre` (present at both the generic `pre` selector and the scoped
`.artifact-document pre` selector), yet the tester found lines clipped mid-token with **no**
scrollbar and **no** wrapping — meaning the declared rule never actually triggered. This is worse
than an aesthetic defect: it is silent data loss against the phase's own core value ("know where
any planning artifact lives ... without reading a single file by hand" — here the reader had no way
to even know text was missing, let alone read it).

### The rule

1. **`pre` never wraps.** `white-space: pre` (never `pre-wrap`) inside code blocks — wrapping breaks
   token alignment and the reader's mental model of line structure. Long lines scroll horizontally
   instead.
2. **The scrollbar must be visibly present, not just technically declared.** `scrollbar-width: thin`
   (Firefox) is necessary but not sufficient on its own — pair it with an explicit WebKit scrollbar
   treatment so the affordance exists cross-browser:
   ```css
   .artifact-document pre::-webkit-scrollbar { height: 8px; }
   .artifact-document pre::-webkit-scrollbar-thumb {
     background: var(--border);
     border-radius: 0; /* squared, per UI-01 */
   }
   .artifact-document pre::-webkit-scrollbar-thumb:hover {
     background: var(--muted-foreground);
   }
   ```
   The scrollbar thumb must have visible contrast against the code block's `--secondary` background
   in **both** themes — do not rely on the browser default track/thumb color, which can render
   invisible against a dark background.
3. **The root cause is an ancestor-chain problem, not a `pre` problem, and the contract must name it
   so the fix does not regress.** A `pre` with `overflow-x: auto` only scrolls internally if every
   ancestor between it and the viewport-constrained shell (`html`, `body`, `#root`) can shrink below
   its content's intrinsic width. Flex and grid children default to `min-width: auto`, not `0` — a
   single ancestor in the chain (a grid cell, `.artifact-document`, and, prior to this revision,
   `.plan-section`) without an explicit `min-width: 0` forces that ancestor to grow to the code
   block's full intrinsic width instead of letting the `pre` scroll internally. The page-level
   `max-width: 100%` shell rule (UI-03) then clips the whole oversized subtree with no scrollbar
   anywhere — which is exactly what the tester observed. **Every ancestor in the chain from `#root`
   to `pre` must carry `min-width: 0`**, not just the `pre` itself. This must be spot-checked against
   the real corpus with a genuinely long unbroken line — a toy fixture with short lines will not
   surface this class of bug, which is exactly how it shipped undetected the first time.
4. **Mermaid diagrams and tables follow the identical containment contract** (already speced under
   UI-03 and unchanged by this revision) — this section's ancestor-chain requirement applies to
   those containers too, not only `pre`.

### Acceptance test

A code block containing a line with a 200+ character unbroken token (no spaces) must, at both
desktop and 390px viewport widths and in both themes: (a) never wrap that line, (b) never truncate
it invisibly, (c) show a scrollbar the reader can see at rest or on hover and use to reach the rest
of the line. Verify against real long-form content, not a synthetic short-line fixture.

## Reference Trigger Resting Appearance (Revision — G-03)

**The prior contract (D-14/D-15, carried forward unchanged below) specified the preview popup in
detail but never specified what the trigger looks like before any interaction.** That is the exact
gap that produced the defect: extraction worked (`references: 5` in the API response), but zero
trigger elements existed in the rendered DOM — there was no visual spec to build against.

### Resting appearance (new)

A resolved reference (the `document-reference` control the linkifier already produces for any ID
with a successful `resolvePresentationReference` match) renders **inline, in running text**, styled
as:

| Property | Value |
|----------|-------|
| Color | `var(--muted-foreground)` |
| Text decoration | `underline`, `text-decoration-style: dotted`, `text-underline-offset: 0.15em` |
| Border / background | none |
| Cursor | `pointer` |
| Font size / weight / family | inherits exactly from surrounding body text — it must read as prose that happens to be interactive, not as a control or a chip |
| Icon at rest | none |

This is **deliberately visually distinct from an authored markdown link** (`.artifact-document a` —
`var(--primary)`, weight 600, solid underline). The two must never converge on the same treatment:
the dotted muted underline signals "clicking this opens a preview first" (D-14's contract), while
the solid accent underline signals "clicking this navigates immediately." If a reference trigger
ever looks identical to a real link, D-14's preview-first behavior becomes visually undiscoverable —
which is effectively what shipped.

**Hover / focus state:** color transitions to `var(--primary)`; `text-decoration-style` switches
from `dotted` to `solid` — the same color and decoration language the popup's own "Open" action
already uses, so hovering a trigger visually rehearses the color it is about to pop up in.

**Focus-visible:** since this is a `<button>`, not an `<a>`, it needs its own visible focus ring —
`outline: 2px solid var(--ring)` (or the app's existing focus-ring pattern) at focus-visible. Do not
rely on the underline-style change alone for keyboard-focus visibility.

popup's "Open" action — and must not be duplicated inline in body text; an inline icon on every
trigger would reintroduce a "chip" reading that contradicts "reads as prose."

## Tables (Revision — G-05)

The tester's verdict was unqualified: "tables look horrible." The observed defects were specific —
cramped first column forcing two-line wraps while the second column ran wide unchecked, no
column-width discipline, no consistent zebra/grouping, and inconsistent hairline weight between the
header rule and row rules.

### Column-width discipline

GSD tables are overwhelmingly ID/label-led (requirement IDs, status words, short keys) followed by
longer descriptive content — so the fix is a **floor on the first column**, not a fixed layout that
would cramp irregular content unpredictably:

```css
.artifact-document table :is(th, td):first-child {
  min-width: 8ch;
  white-space: nowrap;
}
```

This reverses the observed defect directly: the short ID-style first column no longer force-wraps
to two lines while a wide, unconstrained second column runs past it. `table-layout: fixed` is **not**
adopted — GSD table content is too irregular in shape for a blanket fixed layout to behave
predictably across all artifact types.

### Hairline consistency

Header/body divider and inter-row dividers must be the **same weight and color token** —
`1px solid var(--border)` — everywhere. The only differentiator between the header row and body
rows is the header's existing background tint (`--secondary`) and label typography (uppercase,
`--font-heading`, smaller size), never a heavier or differently colored rule. No vertical cell
borders — GSD tables read as horizontally-ruled only (this was part of what read as "cramped").

### Zebra striping

Keep and universally apply the existing treatment — it was not itself rejected, only the overall
table package was:

```css
.artifact-document table tr:nth-child(even) td {
  background: color-mix(in oklch, var(--muted) 38%, transparent);
}
```

Apply to every table inside `.artifact-document` consistently, not selectively.

### Overflow behavior (unchanged)

When a table exceeds the reading column's width, it scrolls horizontally inside its own
`overflow-x: auto` boundary exactly as already specified under UI-03 — this part of the prior
contract passed UAT and is unchanged. The table keeps `width: max-content` so columns are never
artificially compressed to fit; the container scrolls instead.

## Badges (Revision — G-07)

`.status-chip` passed contrast but read as weak per the tester ("could be improved"). This is a
tightening of the existing three-tone system (`active`/`complete`, `quiet`, default/neutral) — no
new tones, no shape change (chips stay squared per UI-01).

- **Neutral/default chips gain a subtle fill.** Previously transparent except for the two
  meaningful tones; every chip should now read as a filled shape, never as outline-only text:
  ```css
  .status-chip {
  ```

## Revision Considerations (Non-Blocking Observations)

Three items were observed while capturing UAT evidence but **were not raised by the tester as
rejections**. They are recorded here with a recommended treatment, per the coordinator's explicit
instruction — **not** as approved requirements for this revision. A future plan may pick these up
without a further UI-SPEC round if it follows the recommended treatment below; if a different
treatment is wanted, that still needs a taste decision first.

### 1. Path-as-title duplication

`.artifact-heading h1` currently renders the artifact's full `.planning/`-relative file path as a
giant multi-line monospace headline, and `.artifact-path` repeats the identical path, verbatim, as a
subtitle directly beneath it — the same string appears twice, at two different type scales, on the
same page.

**Recommended treatment:** H1 shows only the artifact's short title or filename (e.g.
`02-04-PLAN.md`, or a humanized document title where the domain model exposes one). The full
`.planning/`-relative path renders exactly once, in the existing `.artifact-path` subtitle position,
in its existing monospace/muted treatment. Do not duplicate the same string at two type scales on
one page.

### 2. Near-empty document outline column at low heading counts

At exactly 2 headings, the outline renders (the existing `< 2` threshold hides it below that), but
it reserves a full sticky rail column that reads as mostly empty whitespace beside just two links.

**Recommended treatment:** either (a) raise the render threshold to `>= 3` headings, or (b) make the
outline column's width `fit-content` (capped, e.g. `max-width: 14rem`) instead of a fixed
grid-column fraction, so a short outline does not reserve disproportionate space. Either is
acceptable; a future plan should pick one rather than doing both.

### 3. Theme default ignores OS preference

`index.html`'s inline theme-init script treats any stored value other than the exact string
`'light'` as dark — including the common case of no stored value at all, i.e. every first visit —
so `prefers-color-scheme: light` is never consulted. A light-preference OS still opens the app dark.

**Recommended treatment:** when `localStorage['gsd-lore-theme']` has no value, resolve via
`window.matchMedia('(prefers-color-scheme: light)').matches` before defaulting to dark. An explicit
prior user toggle (a real stored `'light'` or `'dark'` value) always overrides the OS preference and
must keep winning. This keeps both themes first-class per UI-02 rather than silently treating dark
as the default.
