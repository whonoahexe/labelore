# Phase 5 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

This phase does **not** introduce a new visual system. UI-04/UI-05/UI-06 require Phase 5 to *write
down* the design language the dashboard, roadmap, traceability and search pages already use, then
hold every new per-type view to it. Everything in this contract below "Design System" through
"Color" is therefore the **existing, shipped** convention (Studio Portal's `base-sera` preset,
locally adapted — `src/web/styles/globals.css` line 22: "Authorized local adaptation of Studio
Portal preset b3Dqcuo4na"), read directly from the codebase, not invented for this phase. What
*is* new is scoped precisely in "New Component Specifications" and "Copywriting Contract" —
the handful of visual/interaction decisions D-01…D-15 leave open.

**Per D-10:** when the eventual `docs/design-language.md` vocabulary test runs against the four
reference pages and one fails, the fix is to add that class name to the doc — never to touch the
reference page. Everything under "Existing Shared Vocabulary" below is the seed list for that doc.

## Spacing Scale

**This phase inherits the project's existing token scale — not the generic 8-point default.**
`quick-260910-jz8` already centralized spacing into named custom properties (`globals.css:172–186`);
introducing a parallel 4/8/16/24px scale would fork the system UI-04 requires be written down as
one convention. Use these tokens exclusively — never a literal `px`/`rem` value in new CSS.

| Token | Value | Use for Phase 5's new elements |
|-------|-------|-------|
| `--space-1` / `--space-1-5` | 4px / 6px | Icon-to-label gaps inside chips and eyebrows (matches `.status-chip` gap) |
| `--space-2` / `--space-2-5` | 8px / 10px | Compact control padding (toggle buttons, chip padding) |
| `--space-3` / `--space-4` | 12px / 16px | Row gaps inside promoted lists (option rows, verification cards, task-index rows) |
| `--space-5` / `--space-6` | 20px / 24px | Padding inside a `.notice`-based unrecognized-type block; gap between a question and its options |
| `--space-7` / `--space-8` | 28px / 32px | Gap between one promoted section and the next inside a view body |
| `--space-fluid-8` / `--space-fluid-12` | clamp(1rem,4vw,3.5rem) / clamp(2rem,5vw,4.5rem) | Already used by `.document-reader-layout` and `.page-intro` — reuse verbatim for any new page-level gap, do not hand-roll a new clamp |

Exceptions: none. The one deliberate non-token value in the whole sheet is the two hand-tuned dark
`--ring`/focus-contrast literals (`globals.css:151`, guarded by
`test/web/focus-ring-contrast.test.ts`) — Phase 5 must not touch those four variables.

## Typography

Full scale is `--fs-1` … `--fs-7` plus fluid/display steps (`globals.css:209–223`); the rows below
are the subset this phase's new UI actually needs. Reuse these, do not add a ninth size.

| Role | Token | Size | Weight | Line Height |
|------|-------|------|--------|-------------|
| Micro label (chips, eyebrow) | `--fs-1` / `--fs-2` | 10.2px / 11.2px | `--fw-semibold` (600) | `--lh-snug` (1.4) |
| Body / list text (option rows, metadata dd) | `--fs-3` / `--fs-4` | 12.2px / 13.1px | `--fw-medium` (500) | `--lh-normal` (1.55) |
| Section heading (promoted-region `h2`-equivalent) | `--fs-6` | 16px | `--fw-semibold` (600) | `--lh-snug` (1.4) |

## New Component Specifications

The genuinely open visual/interaction decisions CONTEXT.md left to discretion (D-07/D-09/D-12/D-13
mechanics) or didn't cover at all (per-type header copy, option-table presentation, verification
card layout, unrecognized marker). Each reuses the shared vocabulary above; new class names are
noted as **shared** (add to `docs/design-language.md`) or **view-local** (reserved-prefix, no doc
entry needed).

### 1. Document source toggle (D-01 / D-03)

Renders inside `ArtifactHeader`'s `children` slot — the exact slot `plan-pair-page.tsx` already
uses for `.plan-pair-jumps`. Not a route change, not anchor navigation: a local two-state toggle
between the promoted view (default) and the full rendered document.

- Markup: `<div className="document-view-toggle" role="group" aria-label="Document display">` wrapping two `Button` (`size="xs"`) instances.
- Labels — exactly two words, matching the app's terse control-copy convention: **"View"** (default/active) and **"Source"**.
- Active state: `variant="secondary"` (filled) + `aria-pressed="true"`; inactive: `variant="ghost"` + `aria-pressed="false"`. The active button's underline/indicator uses `--primary` per the accent-reservation list above — do not tint the inactive button.
- Class: `.document-view-toggle` — **shared** (every view uses it identically).
- Switching is client-side state only; per Phase 2's D-16, it must not push a new URL entry or a `#hash`.

### 2. Collapsed remainder disclosure (D-02)

Reuses the existing `<details className="artifact-metadata">` pattern verbatim — same border,
same `.card-veil` background, same `<summary>` + trailing count-span shape already shown for
"Document metadata".

- Summary copy: **"More in this document · {N} sections"** (N = count of unpromoted top-level sections). Exact mirror of the existing `Document metadata <span>{N} sections</span>` phrasing.
- Placement: after the promoted region, in document order (D-02), as the *last* item — also the final entry the outline lists (D-11: "the collapsed remainder as a single entry").
- If the manifest promotes every section (N = 0), omit the disclosure entirely — do not render an empty one. This is the same "silently omit" rule as D-06, applied to the remainder itself.
- No new class needed — this is a `.artifact-metadata` reuse, already in the shared vocabulary.

### 3. DISCUSSION-LOG view (VIEW-02 proof case)

Per question (one `splitSubsections` result):

- Question heading: reuse `.section-heading.compact` (the existing bordered-icon-well heading pattern already used elsewhere for numbered/counted headings) with the question text as its label. Do not introduce a bespoke `<h3>` style.
- Options: `<ul className="view-discussion-log-options">` (**view-local**), one `<li className="view-discussion-log-option" data-chosen={boolean}>` (**view-local**) per row.
  - The chosen option: leads with `<span className="status-chip" data-tone="active">Chosen</span>` (shared chip, accent-tinted per the color contract above) followed by the option's `Description` text at `--fs-4` / `--fw-medium`.
  - Every other option: plain text at `--fs-3`, `--muted-foreground` — no chip, no strikethrough (D-04 doesn't ask for re-ranking, only for showing what was offered).
  - Order: table row order, unchanged (this is the file's own order, not a promotion-order concern).
- If `parseMarkdownTable` finds no row with `Selected === '✓'` for a question (malformed source), omit that question from the promoted region per D-06 — it falls into the D-02 collapsed remainder instead of rendering with a missing "Chosen" state. Never render a question with zero chips and zero indication.
- Zero-one-many: a log with exactly one question still gets the full heading treatment (no special-cased singular layout); a log with many questions relies on the page's existing `--space-7`/`--space-8` section gaps — no pagination, no cap (survey confirms typical volume is single-digit questions per log).
- Long text: option `Description` text wraps normally (`overflow-wrap: anywhere`, matching `.artifact-document`'s existing rule) — never truncated or clamped.

### 4. VERIFICATION view (VIEW-03)

Leads the page (D-04: manifest order, not document order) with the `human_verification[]` array,
promoted straight from `artifact.frontmatter` (Frontmatter Projection, no handler work).

- Section heading: `.section-heading` reading **"Needs human verification"**.
- Each check: reuse `.metadata-list` (the existing dt/dd field-list styling from `MetadataPanel`) rather than a bespoke card — three labeled fields:
  - `<dt>Check</dt><dd>{test}</dd>`
  - `<dt>Expected</dt><dd>{expected}</dd>`
  - `<dt>Why a person</dt><dd>{why_human}</dd>`
- Wrap each check in `<div className="view-verification-check">` (**view-local**, spacing/border grouping only — the field styling itself is the shared `.metadata-list`).
- Empty array (`human_verification` absent or `[]`): omit the whole "Needs human verification" section per D-06 — do not render the heading with an EmptyState under it. A VERIFICATION file with nothing needing a human is a legitimate, silent case.
- Long text: `expected`/`why_human` are free text and may run to a full sentence or more — `dd` wraps normally, no truncation.

### 5. PLAN task-structure index (VIEW-04)

A promoted summary ahead of the plan body, built from the same `data-plan-ordinal` /
`data-plan-section` / `data-plan-gate` attributes `renderPlanRange` already emits (Tag Projection,
no new parsing) — not a duplicate of the outline.

- `<ol className="view-plan-task-index">` (**view-local**), one `<li data-gate={boolean}>` per segment, in ordinal order.
- Each row: ordinal (`--font-heading`, `--fs-1`, muted) + the section's tag label (`--fs-4`, `--fw-medium`) + a trailing chip only when `data-plan-gate` is present: `<span className="status-chip" data-tone="active">Gates</span>`.
- Ungated rows show **no chip** — do not use `data-tone="quiet"` here as a "not gated" marker; absence of a chip already communicates it, and adding one would dilute the 10% accent reservation.
- **Does not cap or truncate at 18 entries** — unlike `DocumentOutline` (a navigation aid, capped for scan-ability), this index's entire purpose is completeness of gating status; every section must appear. If the list runs long, it scrolls with the page, not in an inner scroll region.

### 6. Outline — reading position (D-11/D-13, wide layout)

No CSS change at ≥58rem: `.document-outline`'s existing sticky-column treatment (`globals.css:2821`)
stays. Only its **data source** changes (view registry's promoted-section list, not
`document.headings`) and it gains an **active-entry** state:

- The currently-intersecting section's `<a>` gets `data-active="true"`.
- Active styling: text color switches from `--muted-foreground` to `--primary` (the same color
  transition `.source-link:hover` already uses — do not invent a new hover-adjacent color), plus a
  `--space-1` (2px)-wide squared bar in `--primary` in the list item's left gutter — same visual
  language as `.status-chip[data-signal='phase']::before`'s squared marker (no rounded dot, no
  pill — squared corners per the Design System table).
- Only one entry is active at a time (D-13: "a single active entry").

### 7. Outline — narrow-width sticky disclosure (D-12, replaces the ≤58rem in-flow rule)

`globals.css:3124–3139`'s current `@media (max-width: 58rem)` rule (which drops `.document-outline`
into normal flow) is replaced, not extended — that rule is the exact pattern D-12 rejects.

- Trigger: a full-width sticky button pinned directly under the page chrome (`position: sticky; top: var(--space-22)` — reuse the same sticky offset the wide-layout outline already uses, so the trigger lands exactly where the sidebar column would have started).
- Trigger label (D-13's own example, verbatim): **"On this page · {current section label}"**. Before any section has been scrolled past, show the first section's label. Trailing `ChevronDown` icon (reused import, matches `.warning-disclosure-chevron`'s icon choice), rotated via `@base-ui/react` Popover's `data-open`/`data-popup-open` attribute — mirror the existing chevron-rotate convention rather than inventing a new one.
- Content: `@base-ui/react` `Popover.Positioner` + `Popover.Popup`, anchored to the trigger, rendering the **same** `<ol>` markup the wide outline uses (reuse `.document-outline ol` styling — don't duplicate it into a second list style). This is the "overlay," not push-content, behavior D-12 requires — `Popover` over a bespoke `<details>` per RESEARCH.md's own recommendation, since `<details>` cannot overlay.
- Class names: `.document-outline-trigger` (**shared** — new, add to `docs/design-language.md`) for the sticky button; the popup content reuses `.document-outline` unmodified.
- Keyboard/focus: standard `@base-ui/react` Popover behavior (Escape closes, focus returns to trigger) — no custom focus trap.

### 8. VIEW-06 — unrecognized-type marker

Two distinct cases per RESEARCH.md's corrected finding — same visual chip, different notice copy.

- Chip (in `ArtifactHeader`'s `chip` slot, same slot the Unreadable/Warning chips already use): `<span className="status-chip" data-tone="quiet">Unrecognized type</span>`. **Not** `destructive`/`warning` tone — an unregistered type is a coverage gap, not a parse failure, matching `EmptyState`'s own "absence is normal, never alarming" philosophy (`empty-state.tsx`'s own comment: "must never read as a warning, a parse failure, or an application error").
- Eyebrow: humanized `artifact.kind` when it is a real, non-`'unknown'` string (title-case, hyphens → spaces — CSS `text-transform: uppercase` on `.eyebrow` handles the rest); literally **"UNRECOGNIZED"** when `kind === 'unknown'`.
- Below the lead, a plain (non-`.destructive`) `.notice` block — same shared component `plan-pair-page.tsx`'s "Outcome not recorded yet" aside already uses, same neutral treatment:
  - Case (a), `kind === 'unknown'` (filename matched no GSD grammar at all): *"This file's name doesn't match a known GSD document pattern, so nothing about its type could be inferred from context. Showing its structure as found."*
  - Case (b), a known-shaped kind with no registered manifest: *"Labelore doesn't yet have a dedicated view for **{kind}** documents. Showing what its headings and structure suggest."*
- Below the notice, the speculative structural read (nested frontmatter → frontmatter projection reusing `.metadata-panel`; stable `##` headings → section projection reusing `.section-heading`; neither → skip straight to the full document, and in that specific sub-case omit the document-source toggle entirely since there is nothing to toggle between).

## Per-Type Header Copy (VIEW-01/05)

Formula: `eyebrow` = humanized `artifact.kind` (hyphens → spaces, CSS uppercases); `lead` = one
sentence, third-person, naming what the reader gets that raw markdown buries — following the phase
goal's own framing ("a discussion log reads as questions and choices…"). `title` is unchanged
(existing `dropLeadingTitle`-derived document title).

Ground truth for the kind-string set is RESEARCH.md's code-traced 16 (`discovery.ts` /
`naming.ts`), **not** ROADMAP.md's illustrative strategy table, which sums to 17 by including the
singleton root files (`ROADMAP`, `REQUIREMENTS`) that already have their own dedicated routes
outside this registry. RESEARCH.md's own Open Question 1 flags this as unresolved — planner/executor
should run the recommended corpus grep before finalizing manifests; extend this table with the same
one-sentence formula for anything the grep surfaces beyond the 16 below (`review-fix` is the most
likely gap).

| `kind` | Lead copy |
|---|---|
| `discussion-log` | Each question, the options that were on the table, and which one was chosen. |
| `verification` | What still needs a human to check, first — then everything already confirmed. |
| `plan` | The task structure this plan commits to, in order, and which sections gate. |
| `summary` | What shipped, against what the plan committed to. |
| `review` | Findings from cross-AI review, by severity. |
| `milestone-audit` | Whether the milestone's own intent — not just its checklist — was met. |

## Copywriting Contract

| Element | Copy |
|---------|------|
