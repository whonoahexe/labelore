## Fixture design

### Q1 — How should the dense fixture be constructed?

| Option | Description | Selected |
|--------|-------------|----------|
| Hand-authored synthetic | Shape derived from `~/.claude/gsd-core/templates/`, not studio-portal. Full control; can include `AI-SPEC.md`/`SPEC.md`, a third milestone, an invented future type. Costs authoring time; files are stubby rather than realistic in length. | ✓ |
| Redacted studio-portal copy | Real structure with placeholder bodies. Realistic scale and naming edge cases for free, but inherits studio-portal's exact artifact set — the shape research warns against overfitting to. | |
| Generated by running gsd-core | Real gsd-core 1.11.0 output; truest fidelity, sparse fixture nearly free. But driving it to genuinely dense means running a lot of workflow, and it cannot produce types GSD doesn't ship yet. | |
| Hand-authored, seeded from templates | Mechanically copy every template file as a skeleton, then hand-edit. Traceability to template lines by construction. | |

**User's choice:** Hand-authored synthetic
**Notes:** The traceability rule from PITFALLS #1 still applies — assumptions should cite a template
line rather than studio-portal — but without mechanically seeding from the template directory.

### Q2 — Where does the deliberately corrupted content live?

| Option | Description | Selected |
|--------|-------------|----------|
| Inside the dense fixture | Broken files among healthy ones. Truest to Criterion 3's "while every other file parses cleanly". Cost: dense golden permanently contains warnings. | ✓ |
| A third, purely-broken fixture | Keeps both goldens pristine and assertable at zero warnings; gives Phase 4 an obvious target. Cost: exceeds DATA-06's "two fixtures"; isolation-among-healthy-files not directly proven. | |
| Both — seeded dense plus a broken one | Most thorough; cleanly splits degradation from refusal. Cost: three fixtures to author and maintain. | |

**User's choice:** Inside the dense fixture
**Notes:** Consequence recorded in CONTEXT.md D-02 — "zero warnings" can never be asserted against the
dense fixture's golden. The hostile cases that would have justified a separate broken fixture are
deferred; they become cheaply authorable via the in-memory filesystem chosen in Harness Q4.

### Q3 — How do we resolve the sparse-fixture contradiction between Phase 1 SC2 and Phase 4 SC1?

*Raised by Claude during analysis:* the roadmap describes the sparse fixture two incompatible ways —
Phase 1 SC2 says "fresh project, no `ROADMAP.md`, no `phases/`"; Phase 4 SC1 says "one phase, no
milestones".

| Option | Description | Selected |
|--------|-------------|----------|
| Two sparse variants | Empty-floor tree plus barely-started tree. Different code paths; each roadmap criterion gets the fixture it names. Cost: three trees total, extending DATA-06's "two". | ✓ |
| Empty floor only | Honors Phase 1's wording; harshest input, exercises every null-check. Cost: the "structure but no history" path — the common early-project case — goes untested. | |
| One phase, no milestones only | Honors Phase 4's wording; more representative of daily use. Cost: the true empty-project path goes untested, which PITFALLS #1 calls out by name. | |

**User's choice:** Two sparse variants
**Notes:** Phase 1's fixture count becomes three trees. Flagged in CONTEXT.md D-03 as something to
surface to the roadmap rather than quietly satisfying DATA-06's letter with the wrong trees.

### Q4 — What role does `~/studio-portal` play in Phase 1's verification?

| Option | Description | Selected |
|--------|-------------|----------|
| Manual smoke target only | Fixtures are the committed asserted suite; studio-portal is eyeballed by hand with no committed assertions. Keeps the machine-checked contract fixture-derived. Cost: real-world-only regressions aren't caught automatically. | ✓ |
| Committed golden snapshot too | Catches real-corpus regressions automatically. Cost: enormous golden, constant churn (studio-portal is actively worked), non-portable test suite. | |
| Smoke target with invariant-only assertions | Asserts only churn-proof shape invariants; skips cleanly when the directory is absent. Cost: one more harness mode to build and keep honest. | |

**User's choice:** Manual smoke target only
**Notes:** Directly serves PITFALLS #1's warning sign — "any function whose only test input is the real
`~/studio-portal` tree".

## Harness shape

### Q1 — What is the harness, concretely?

| Option | Description | Selected |
|--------|-------------|----------|
| CLI plus golden tests | `npm run snapshot -- <path>` prints JSON; Vitest suite invokes the same entry point against fixtures and diffs a committed golden. Shared entry point prevents the tested path diverging from the runnable one. | ✓ |
| CLI only | Simplest thing satisfying DATA-05's literal wording; no goldens to churn. Cost: no automatic regression catching — verification becomes a human reading a large JSON blob. | |
| Golden tests only | Least code; `vitest -u` regenerates on intentional change. Cost: no ergonomic way to target an arbitrary path, making TGT-01/TGT-02's path-form proof awkward. | |
| CLI, goldens, and a summary mode | Adds a compact human digest — counts by kind, tree outline, warnings, unresolved refs. Cost: a second output format to keep in sync. | |

**User's choice:** CLI plus golden tests
**Notes:** The summary mode was noted as genuinely useful against a full studio-portal dump and carried
forward as a deferred idea rather than dropped.

### Q2 — Does the dumped JSON include every artifact's full markdown body?

| Option | Description | Selected |
|--------|-------------|----------|
| Omit bodies by default, flag to include | Structure, frontmatter, cross-refs, warnings, plus body length and hash. Readable diffs; hash catches truncation. Cost: length-preserving body mangling invisible without the flag. | ✓ |
| Always include full bodies | Most literal reading of DATA-05; golden genuinely proves nothing is lost. Cost: large goldens, unreadable diffs, one-character prose edits rewriting the file. | |
| Never include bodies | Smallest cleanest goldens. Cost: Criterion 3's "degrades to its raw body" becomes uncheckable through the harness. | |

**User's choice:** Omit bodies by default, flag to include
**Notes:** The flag is not optional polish — it is what keeps Criterion 3 provable.

### Q3 — How does the harness handle machine-varying values in golden output?

*Raised by Claude:* `mtimeMs` and absolute paths both appear in `ARCHITECTURE.md`'s `RawArtifact`/
`Artifact` shapes, and both change on every clone — a committed golden would fail immediately and
permanently.

| Option | Description | Selected |
|--------|-------------|----------|
| Normalize in a serializer | One step replaces absolute paths with root-relative and mtimes with a placeholder under `--stable`; raw CLI dump keeps real values. All machine-variance owned in one function. | ✓ |
| Keep paths relative in the model itself | Path variance disappears at the source; makes containment checks natural. Mtimes still need handling. Cost: re-joining to root wherever a real path is needed. | |
| Both | Model clean by construction plus serializer protection for future volatile fields. Cost: more ceremony for a currently two-field problem. | |

**User's choice:** Normalize in a serializer

### Q4 — How is Criterion 4 (swappable filesystem) proven rather than asserted?

| Option | Description | Selected |
|--------|-------------|----------|
| In-memory FS fixture implementation | A second `PlanningFilesystem` over a `path → content` map runs the same golden tests; byte-identical output proves the seam by construction. Also speeds fixture tests and enables hostile cases awkward to commit. | ✓ |
| Lint rule plus code review | ESLint forbidding `node:fs` outside `src/planning-fs/`. Cheap, catches the real failure mode. Cost: proves "nothing imports fs", weaker than "a different source produces the same snapshot". | |
| Both | Prevention plus proof. Cost: most Phase 1 work of the three. | |

**User's choice:** In-memory FS fixture implementation
**Notes:** The lint rule was noted as cheap ongoing enforcement worth adding later and carried forward
as a deferred idea.

## Degradation & warnings

### Q1 — Where do warnings live on the snapshot?

| Option | Description | Selected |
|--------|-------------|----------|
| Both root list and artifact | Flat `snapshot.warnings[]` plus a per-artifact reference. Same objects, two access paths. Cost: two places to keep consistent, so both must be built from one source. | ✓ |
| Root list only | One source of truth, trivially serializable. Cost: pushes the path-filter join onto every consumer. | |
| On the artifact only | Degradation sits next to the thing degraded. Cost: warnings belonging to no artifact — an unlistable directory, an unreadable file that never became an artifact — have nowhere to live. | |

**User's choice:** Both root list and artifact

### Q2 — Are unresolvable cross-references warnings?

| Option | Description | Selected |
|--------|-------------|----------|
| Separate — not warnings | `{ raw, resolved: null }` on the graph, out of the warning channel. Dangling refs are expected, not exceptional. Cost: a typo'd ID looks identical to a deliberately-unlinked mention. | ✓ |
| Warnings at an info severity | One channel with a severity field; ready-made health feed. Cost: info tier dominates by an order of magnitude, making warning counts meaningless without filtering. | |
| Separate, plus a rollup count | Keeps the channel meaningful while surfacing "47 dangling IDs" at a glance. Cost: one more derived field to keep accurate. | |

**User's choice:** Separate — not warnings
**Notes:** Grounded in `ARCHITECTURE.md`'s explicit "dangling references are expected, not
exceptional", and in this project's own `STATE.md` containing literal `[Phase ?]:` placeholders. The
rollup count was carried forward as a deferred idea for Phase 4's health surface.

### Q3 — What does a single warning record carry?

| Option | Description | Selected |
|--------|-------------|----------|
| Path, stage, message, salvage | `stage` = read/frontmatter/structured-extraction/assembly; `salvage` = what survived. Makes PITFALLS #4's frontmatter/body independence expressible. Phase 4 reads empty states off these fields. | ✓ |
| Path and message only | Minimal; enough for a solo tool. Cost: consumers must pattern-match message text to distinguish failure kinds, which breaks on rewording. | |
| Add the underlying error too | Useful for unanticipated fixture failures. Cost: stack traces are machine-varying and become one more thing the normalizing serializer must strip. | |

**User's choice:** Path, stage, message, salvage
**Notes:** Capturing the underlying error was carried forward as a deferred idea.

### Q4 — What does the read layer return when the target isn't a GSD project?

| Option | Description | Selected |
|--------|-------------|----------|
| A snapshot with a `loadStatus` field | `load()` always resolves; status is `ok`/`not-a-gsd-project`/`path-not-found`/`permission-denied` plus the exact path checked. One shape for every consumer; Phase 4's error screens are just another render. Cost: consumers must check rather than being forced by an exception. | ✓ |
| Throw a typed startup error | Impossible to ignore; keeps the snapshot type honest. Cost: two failure mechanisms in the read layer; "this project failed to load" is harder to represent as data later. | |
| Result union — loaded or failed | TypeScript forces both arms; snapshot type stays clean. Cost: every call site unwraps, including the many that only see the happy path. | |

**User's choice:** A snapshot with a `loadStatus` field
**Notes:** This is the one case `ARCHITECTURE.md` carves out of "always produces a snapshot"; resolved
here in favor of one uniform shape. Also noted as forward-compatible with a multi-project switcher
holding a failed project alongside good ones.

## ID scanning rules

### Q1 — Which ID schemes does the Phase 1 prose scanner recognize?

| Option | Description | Selected |
|--------|-------------|----------|
| The four Phase 2 needs, plus decisions | Requirement IDs, phase references, plan IDs, decision IDs — exactly what NAV-02/03/07 consume. Others recorded only where already structured in frontmatter. | ✓ |
| Every scheme in the domain research | All nine catalogued schemes; maximally complete index. Cost: the riskiest schemes have no distinctive shape — bare integers for waves and ledger entries match any number anywhere. | |
| Requirements and decisions only | Narrowest set satisfying NAV-07 plus the requirement half of Criterion 5. Cost: NAV-03 lands in Phase 2 with no index behind it. | |

**User's choice:** The four Phase 2 needs, plus decisions

### Q2 — How does the scanner handle the `D-NN` vs `D1` collision?

| Option | Description | Selected |
|--------|-------------|----------|
| Resolve within artifact-type context | Exactly `GSD-DOMAIN.md`'s prescription — never a single global namespace. Cost: the scanner needs the artifact's kind, so it runs after dispatch rather than alongside discovery. | ✓ |
| Require the hyphen | Trivially unambiguous, zero context needed. Cost: a convention bet — `D5` for a decision or `D-1` for a deliverable silently corrupts the index. | |
| Record both, mark ambiguous | Loses nothing; Phase 2 renders ambiguous mentions as plain text. Cost: pushes the call to a phase with less information to resolve it. | |

**User's choice:** Resolve within artifact-type context
**Notes:** The structural consequence — scanner runs post-dispatch, not during discovery — is recorded
in CONTEXT.md D-14 as a constraint on the pipeline ordering.

### Q3 — Does the scanner look inside fenced code blocks and inline code spans?

| Option | Description | Selected |
|--------|-------------|----------|
| Skip both | Excludes constants, hyphenated identifiers, CSS tokens, branch names like `feat/AUTH-02`. Cost: GSD authors quote IDs in backticks constantly, so those references are missed. | ✓ |
| Skip fenced blocks, scan inline code | Matches how GSD authors actually write. Cost: inline spans also hold real paths and identifiers; the distinction is a heuristic about intent. | |
| Scan everything | Simplest rule, nothing missed. Cost: guaranteed false positives; Phase 2's linkifier inherits the problem. | |

**User's choice:** Skip both
**Notes:** The inline-spans-yes/fences-no option was recorded in CONTEXT.md as the specific relaxation
to try if this proves too lossy — explicitly *not* "scan everything".

### Q4 — What does each recorded mention carry?

| Option | Description | Selected |
|--------|-------------|----------|
| Artifact ref, position, and excerpt | Matches `ARCHITECTURE.md`'s "mentioned in 3 places with excerpts". Position enables Phase 2 deep-links (READ-06) and saves Phase 3 recomputing snippets. Cost: larger records; positions must survive the serializer. | ✓ |
| Artifact ref only | Exactly NAV-07's literal wording. Cost: any excerpt or deep-link means re-scanning at render time — "eager resolution with extra failure modes, not less work". | |
| Artifact ref and first-seen excerpt | Matches the research's literal phrasing; gives a decision page something to show. Cost: no deep-linking; repeated mentions in one file indistinguishable. | |

**User's choice:** Artifact ref, position, and excerpt

## Claude's Discretion

locked — the planner decides them and records the outcome:

- **Structured-extraction depth** — how deep typed handlers parse in Phase 1 versus Phase 2. Flagged as
  the decision most likely to shape how the phase's two plans get split.

  #9 supplies the constraints; the `loadStatus` values from Degradation Q4 are the agreed output shape.

No question in this discussion was answered with "you decide".
