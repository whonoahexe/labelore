> Visual and interaction contract for the Codebase page (seven map documents on one page), the
> "mapped, not started" first screen, and the six specification and check pages (Spec, AI spec,
> User setup, Eval review, Browser check, Cross-AI reviews), plus the made-up example rule that binds

> Sources: 10-CONTEXT.md (D-01 to D-15, locked), ROADMAP.md Phase 10 success criteria, REQUIREMENTS.md
> (VIEW-11, VIEW-12, VIEW-13, VIEW-21, TGT-09), `docs/design-language.md`, the shipped Research page

## Contract split (read this first)

This contract locks what every page in the phase shares: tokens, tones, chips, squares, copy, states,
the generic-page fallback, accessibility and the made-up example rule. It does **not** prescribe a page
frame. Each page's arrangement is decided by its own sketch (D-14), and no page reuses the previous
sketch's frame (user rule, `sketch-fresh-structure`). The "Must show" lists below are the content
each page promises (they come from the success criteria); the sketch decides the order, the
weight and the arrangement. If a sketch winner cannot carry an item in a "Must show" list, the plan
records the deviation; it does not silently drop the item.

## Spacing Scale

Declared values (all multiples of 4), applied through existing tokens:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px (`--space-1`) | Icon and square to text gap, chip gap, segmented-meter cell gap |
| sm | 8px (`--space-2`) | Gap between a row's chips; gap between a label and its value |
| md | 16px (`--space-4`) | Row padding, tile padding, gap inside a group |
| lg | 24px (`--space-6`) | Gap between groups and sections; panel padding |
| xl | 32px (`--space-8`) | Gap between a main column and a side column; page top rhythm (through `page-stack` / `--space-fluid-*`) |
| 2xl | 48px | Not used by this phase |
| 3xl | 64px | Cover/head vertical padding only, through `--space-fluid-*` |

Exceptions:
- Spine, rail and square geometry a sketch locks are decoration, not layout spacing. They are written as
  `calc()` over `--space-*` tokens where an exact token exists, otherwise as one named custom property per
  view (the Phase 9 `--view-project-node-offset` precedent). No bare `px` or `rem` in a rule (design language: token-only spacing).
- Copy-command button, panel switch controls and tab links keep a hit area of at least 40px high under
  `@media (pointer: coarse)` (the `Button` size `sm` step); fine pointers keep the `xs` 28px.
- A mono command or path never sets the height of its row: it ends in an ellipsis on one line with the
  full value in `title`, except the copyable command, which wraps (see Layout 2).

### Tone mapping (document content only)

The four-square vocabulary (`status-square`, `data-tone`) is the one Phase 9 promoted to a shared name.
Reuse it. A square is never the only carrier of meaning: it always sits beside a word or has an
`aria-label`. Chips are `status-chip` with `data-tone`.

| Meaning | Tone | Mark |
|---------|------|------|
| Finished, covered, passed, verified, agreed | `complete` | square filled `--primary` |
| Waiting on someone, partial, needs a person, below target | `in-flight` | square filled `--in-flight-fill` |
| Expected and absent, failed, blocking | `missing` | square outlined 2px `--missing-fill` |
| Neutral, not applicable, unfilled, unknown, could not look | `quiet` | square dashed `--muted-foreground` |

### Page-by-page tone use (default mapping; a sketch may refine within these four tones only)

- **Codebase page and head.** "Complete" map readiness `complete`; "Fast" `in-flight` ("a partial map; complete map still needed"); a document missing from the folder: `quiet` dashed, "Not mapped". Concerns: counts per section are plain numerals (Heading, mono) on a neutral square; the **Security** section's count carries `in-flight` when above zero and `complete` ("0") when zero; no concern section is ever `missing` or `destructive` (a concern is a finding about code, shown as content). Stack chips (languages, frameworks, runtime) are untoned `status-chip`s with the version in mono; the `NEW / EXTEND / MODIFIED / EXISTING` tree badges keep their existing mapping when the Structure panel shows a tree. The "Last mapped" commit stamp is a mono `quiet` chip.
- **Spec.** Ambiguity score against the gate (GSD's gate: score ≤ 0.20): at or below the gate `complete` "Locked enough to plan"; above the gate `in-flight` "Not locked yet"; a score the page cannot read `quiet` "Ambiguity not stated" (score shown verbatim when present). Requirement rows: Current / Target / Acceptance are labelled fields, not toned; a requirement missing its Acceptance line shows a `quiet` dashed chip "No acceptance stated". Boundaries: In scope `complete` square, Out of scope `quiet` square.
- **AI spec.** Checklist item done `complete`, not done `quiet` (dashed). A section that is still the template's placeholder text: `quiet` chip "Template slot" (never `in-flight`, never `missing`: an unfilled slot is an absence of authoring, not a failure). The lead line counts them ("3 of 8 sections are still template slots"). System type, framework and evaluation-dimension names are untoned chips.
- **User setup.** Step done `complete`; step pending `in-flight` (waiting on a person); a step the page cannot classify `quiet`. A variable row carries a `quiet` "Value not shown" mark. Nothing here is `missing`.
- **Eval review.** Verdict chip, GSD's four verdicts verbatim: PRODUCTION READY `complete`, NEEDS WORK `in-flight`, SIGNIFICANT GAPS `missing`, NOT IMPLEMENTED `missing`; any other or absent verdict `quiet` "Verdict not stated". Dimension coverage: COVERED `complete`, PARTIAL `in-flight` (GSD calls it WARNING), MISSING `missing` (GSD calls it BLOCKER). Score numerals are not toned.
- **Browser check.** Outcome chip: `verified` `complete`; `nothing_to_report` `quiet` "Nothing to report" (a clean result with no criteria to check, not a pass); `could_not_look` `in-flight` **with a distinct icon and the reason named** ("Could not look: target unreachable"), so it is visibly different from "Nothing to report" in shape and words, not colour alone. Counts: passed `complete`, failed `missing`, needs review `in-flight`; a zero count is shown as `0` with a dashed square, never hidden.
- **Cross-AI reviews.** Reviewer cards are untoned (name, model, run status). A concern's severity: HIGH `missing`, MEDIUM `in-flight`, LOW `quiet` (GSD's words, the research pitfalls mapping). Overall risk likewise by LOW/MEDIUM/HIGH. **Agreed** concerns carry no tone of their own (they take their severity's); the group is headed "Agreed". A **disagreement** is a `quiet`-bordered block that shows each reviewer's stance side by side and a `status-chip` "Reviewers disagree" on `in-flight` (waiting on a person to decide). The signals are never merged into one verdict ("keep disagreeing signals separate", PROJECT.md).

### Accent reserved for, in this phase's new UI, exactly these

1. The `.eyebrow` kind label on each new page (existing rule reused verbatim).
2. `complete`-tone marks as listed above (complete map, locked spec, done AI-spec/user-setup items, PRODUCTION READY, COVERED, verified/passed, "0 security concerns"). They share the existing `complete` styling; nothing is tinted by hand.
3. The active panel's number and pressed-chip state on the Codebase page, and the current panel's border, exactly as Research 031 already spends the accent (the pressed state `--primary-tint` and accent border of `research-chip`; the leaf's big number). The Codebase page may spend no other accent.
4. The Architecture and Structure panels' figures: lifted-diagram arrows, hovered card, clean-tree folder icons, the selected lane node (already reserved by the design language for figures).
5. The copy-command button's keyboard focus ring and hover underline only (`--ring` is `--primary`). The button is not an accent-filled primary button: this is a read-only app, so no accent-filled call to action exists on any page.
6. The keyboard focus ring (global).

Expected density: accent is the eyebrow, a few `complete` squares and the active panel number; well under a tenth of the visible area on every page.

Not accent: links (`.text-link` / `.source-link` as they stand), the pressed switch (the `secondary` button variant), `in-flight` / `missing` / `quiet` marks, headings, numerals, severity chips, the stack chips, the figure's lanes and edges.

Focal point per page: Codebase head, the readiness chip beside the next-step command; Spec, the ambiguity score against the gate; AI spec, the unfilled-slot count; User setup, steps done of total; Eval review, the score and verdict; Browser check, the outcome chip; Reviews, the "Agreed" concerns group, then the disagreements.

## Layout and Interaction Contract

### 1. Shared rules (bind every page)

1. **Every page is a document page.** `ArtifactHeader` unmodified: breadcrumbs, copy-path button, View/Source toggle. Source mode shows the whole raw file. Pages do not name their source file in prose (dashboard rule).
2. **Nothing is dropped.** Anything the view does not claim stays reachable: either rendered as a plain readable section below the designed part (Codebase, D-02) or listed in an "In the source only" strip that links into Source mode at the heading (the Research/UI-SPEC precedent). A section that matches no known heading is shown, not hidden.
3. **Read-only, no state beyond the page.** The only client state is panel selection (via URL on the Codebase page), disclosure open state, "Read more" and any switch the sketch adds; all local, all lost on reload (as every other view). The one write-shaped affordance is **copy to clipboard** (command, path, line), which reads the page and writes nothing.
4. **Absence is silent** unless a specific absence is the point of the page (design language: `Nothing here yet.` is the only sanctioned generic absence string, and only when a visible absence surface is genuinely needed). A page whose point is an absence ("not mapped", "Nothing to report", "template slot") says it in specific words from the Copywriting Contract.
5. **Document text is shown verbatim** through the existing inline tokenizer; the page never re-words an author's requirement, concern, reviewer text or step.
6. **Made-up examples look like any other document.** The UI has no "made up" chip and does not read the marker (D-10). Reversible: a chip could later read the same marker.
7. **Tone is never colour alone**: every square or chip carries a word; every icon-only control carries `aria-label` and `title`.

### 2. Codebase page (VIEW-13; frame from its own sketch, modelled on Research 031)

Route: `/{project}/codebase/{doc}` for `stack`, `architecture`, `structure`, `conventions`, `testing`,
`integrations`, `concerns` (Phase 7 scheme; the addresses already exist in `routes.ts`). All seven open
the **same page** on a different panel (D-01). The URL picks the panel; switching panel changes the
address (a real `Link`, so back-button and deep link work). `/{project}/codebase` with no doc opens the
first mapped panel in the page's order (Stack, Architecture, Structure, Conventions, Testing,
Integrations, Concerns) unless the project is map-only, where it is the mapped-not-started screen (section 3).

**Must show (page level):**
- The page title and a facts line: how many of the seven documents exist ("7 of 7 mapped", "4 of 7 mapped"), **map readiness** as a chip (Complete / Fast, see below), and when the map was made.
- The panel list: seven entries in the fixed order above, each with its number, name and one key number (see below). A document missing from the folder shows as **"Not mapped"** (`quiet`, dashed square, not a link), never hidden. The order does not follow the mapper's file order.
- Map readiness follows GSD's `map_readiness` exactly (`onboard-projection.cjs`): **complete** when all seven documents are present; **fast** when STACK, INTEGRATIONS, ARCHITECTURE and STRUCTURE are present but not all seven; otherwise **none**, which the page words as "Partial map" with the list of present documents and no readiness claim beyond that. The page states which, once, in the facts line.
- "When the map was made": from frontmatter `last_mapped_at`; else the older `**Analysis Date:**`; else `*Last updated:*`; else an `<!-- refreshed: DATE -->` comment; else nothing (silent). The commit stamp (`last_mapped_commit`) is shown **as text only** in a mono `quiet` chip (the read-only filesystem cannot compare it against HEAD, and the page does not claim the map is fresh or stale).

**Panels.** Each panel lifts what it can by **fuzzy heading match** (D-02): case-insensitive, tolerant of a leading emoji or number, of `&` against `and`, of plural/singular, and of an added word ("Languages & Runtimes", "API Architecture"). What matches is rendered in the panel's designed form below; **every section that matches no known heading renders as a plain readable section after the lifted part**, with its own heading, in document order. The generic `artifact-document` rendering is the plain form. A panel with no recognised heading at all is that plain rendering in full (so the page never reads worse than the generic document).

| Panel | Lifts (when the heading matches) | Key number in the panel list |
|-------|----------------------------------|------------------------------|
| Stack | Languages (primary, secondary), Runtime, Frameworks (core, testing, build/dev) as chips with versions; Key Dependencies; Configuration; Platform Requirements | count of languages + frameworks |
| Architecture | System Overview diagram first (the lifted-diagram figure, with the lane diagram only if the graph is confident, and the "Shown as drawn" rule); Component Responsibilities table; Pattern Overview; Entry Points; Anti-Patterns as swaps (what happens -> why it is wrong -> do this instead, the 032 treatment); Layers, Data Flow, Key Abstractions, Constraints, Error Handling, Cross-Cutting as plain sections | components or layers |
| Structure | Directory Layout as the clean tree (`FigureFrame`, titled "Directory structure"); Directory Purposes; Key File Locations; Naming Conventions; **Where to Add New Code** as a lookup (a labelled list, "I want to add ... -> put it in ..."); Special Directories | directories |
| Conventions | Short rules list per heading (Naming, Code Style, Import Organization, Error Handling, Logging, Comments, Function Design, Module Design). Reference material, low urgency: quiet, compact | rule groups |
| Testing | Framework and runner; **run commands as copyable mono rows**; File Organization; Mocking; Fixtures; Coverage; Test Types; listed gaps | framework name |
| Integrations | External services, Data Storage, Authentication, Monitoring, CI/CD, Webhooks as grouped rows; **environment variable names only, never values** (see Safety rule below) | services |
| Concerns | **Count per section** (Tech Debt, Known Bugs, Security Considerations, Performance Bottlenecks, Fragile Areas, Scaling Limits, Dependencies at Risk, Missing Critical Features, Test Coverage Gaps); **Security first**, then the rest in document order; each concern readable in full on demand | total concerns |

A concern count is the number of top-level items under that heading (list items, table rows, or `###`
subsections, whichever the section uses, counted by the same rule on every map). A section with no items
shows `0` (dashed square), not hidden. The Concerns panel may offer **one quiet "Most dangerous" pull
line** (the first item under Security, else the first under Tech Debt), labelled and muted, only if its
sketch earns it; it is never toned `missing`/`destructive`.

**Safety rule (Integrations and Testing).** Environment configuration lists variable **names**. If a map
document states a value next to a name (`KEY=abc123`, `KEY: sk-...`), the lifted row shows the name and
"Value not shown", exactly as the User setup page does. The plain-section remainder and Source mode are
the document as written (this phase adds no masking beyond Phase 6's `config.json` rule); the plan
confirms whether a map value can reach search and, if so, records it as an open item rather than
widening scope (see UI Considerations, open items).

**Panel states.** Panels are cross-read (stack <-> integrations, architecture <-> structure) which is why
they share one page: a cross-reference the author wrote as a `.planning/codebase/...` path or a
"see STRUCTURE.md" mention becomes an in-page link to that panel. Only a reference that resolves is a link.

**Map navigation in a normal project** (a roadmap and a map, Claude's Discretion): the Codebase page is
reached the way Research is reached today (the planning-files drawer and search at least; a header entry
only if Research has one). The plan confirms against `project-layout.tsx` and the drawer; this contract
adds no new header entry on its own. In a project with a roadmap, `/{project}/codebase/{doc}` is the
Codebase page with no mapped-not-started head.

### 3. Mapped, not started (TGT-09; D-04 to D-09)

**When.** The project's first screen is the mapped-not-started screen when `.planning/codebase/` exists
and there is **no `ROADMAP.md` and no phases** (D-04). Stray extras (a `CHANGELOG-*.md`, `ui-reviews/`, a
lone `PROJECT.md`) do not stop it and stay reachable from the drawer. Once a roadmap appears, the normal
dashboard and tabs return. A `.planning/` with neither a map nor a roadmap is out of scope and unchanged
(D-08).

**One page, nothing rendered twice (D-05).** The first screen is a **short head over the Codebase
page's panels on the same screen**; the head is not a second page and the panels are not copied into it.

**Head must show, in a sketch-decided order and arrangement:**
1. The words **"Mapped, not started"** (the eyebrow or the title's lead, the sketch decides) and one sentence: "This project has a codebase map and no roadmap yet."
2. When the map was made and, where the map carries one, the commit stamp, as text (section 2 rules).
3. **Fast or complete**, as the readiness chip from section 2.
4. The **stack lifted**: languages, runtime and frameworks as chips with versions (from the Stack panel's lift; nothing new is parsed for the head).
5. The **concerns lifted**: the counts per section, Security first (from the Concerns panel's lift).
6. **GSD's suggested next step as a copyable command** (D-06), see below.
7. The seven documents as the way in: the panel list of section 2, which is what the panels "below" are.

**Next step (D-06), following `onboard-projection.cjs`, in this precedence:**

| Condition | Command shown | Reason line (Meta) |
|-----------|---------------|--------------------|

**Header and navigation (D-07).** For a map-only project the header **hides Roadmap and Traceability**,

The dashboard route for a map-only project is this screen. The drawer still lists everything.

**Opening (D-09).** A map-only project opens from the project path **or** the `.planning` path, from the

### 4. Specification pages (VIEW-11; frame from each page's own sketch)

Routes follow Phase 7: `/{project}/phase-N/spec`, `.../ai-spec`, `.../user-setup` (and the quick-task and
archived-phase equivalents); the planner confirms the kind names and addresses against `folders.ts` and
`routes.ts`. Each is a document page.

**Spec — must show:**
- **Whether it is locked enough to plan**: the ambiguity score against the gate, as a verdict chip plus the numbers ("0.14 against a gate of 0.20"). Gate read from the file (`(gate: ≤ 0.20)`); 0.20 when the file states a score and no gate; no verdict when no score.
- The goal sentence, then **each requirement** as a numbered item with its short label and, as labelled fields, **Current**, **Target** and **Acceptance** (the three fields GSD's template requires). The count ("5 requirements locked") from the file's `Requirements: N locked`, else counted.
- Boundaries: In scope and Out of scope lists (Out of scope items keep their "— reason").
- Background, Constraints, Acceptance Criteria and any other section the page does not claim: plain sections or the "In the source only" strip.
- The made-up pair (D-11) must cover **one spec below the gate (locked) and one above it**.

**AI spec — must show:**
- **System type, framework, evaluation dimensions and checklist progress** ("5 of 12 checklist items done"; the segmented meter of `status-square`s), taken from the template's own fields.
- **Plainly says when sections are still unfilled template slots**: a lead line with the count and each such section marked with the `quiet` "Template slot" chip. A section is "unfilled" when its body is empty or still the template's placeholder text (bracketed `[...]` prompts or HTML-comment guidance left in place). The detection list is built from the real `templates/AI-SPEC.md` placeholders, not from the made-up file, and the plan names the rule it uses. An unfilled section is shown collapsed with its heading and the chip, never rendered as if it said something.
- The rest of the document as plain sections; the unfilled template instructions are not shown as content.

**User setup — must show:**
- **How many steps are done** ("2 of 5 steps done") with the segmented meter, and each step's status.
- **Where each variable goes**: variable name (mono), the file it goes in (`.env.local`), and where to get it (the dashboard path or URL as text), as GSD's `user-setup.md` template lays out.
- **Never the variable's value.** If the file contains a value (`KEY=...`, a pasted token), the view shows the name, the destination, and the `quiet` "Value not shown" mark. The value does not appear in the View-mode DOM, not in a `title`, not in an `aria-label`, and not in a copy button. The made-up example **includes a value-looking string beside a name on purpose** so the test can assert it is absent from the rendered View output. The plan confirms whether the value can reach Source mode, search snippets or the index and, if it can, records it as an open item (Phase 6 masks only `config.json`), not as a scope change here.
- Step instructions and dashboard configuration notes are shown as written (they are text for a person), collapsed per step with the step's title and status always visible.

### 5. Check pages (VIEW-12; frame from each page's own sketch)

**Eval review — must show:**
- **Score and verdict first**: the overall score ("61 of 100", mono, Heading) and the verdict chip with GSD's verdict verbatim (see Tone mapping). The page shows GSD's numbers as written and never recomputes them (the auditor's own rule).
- **Dimension coverage**: one row per eval dimension with its COVERED / PARTIAL / MISSING state, how it is checked (Code / LLM Judge / Human) and the finding; a summary tally ("4 covered, 2 partial, 1 missing") with the segmented meter. Infrastructure audit (`ok`, `partial`, `missing` per component) as a second, smaller group when present.
- **Ordered remediation plan**: the plan's steps in the author's order, numbered, each tied to its dimension where the file names one, with PARTIAL and MISSING distinguished by their marks.
- Anything unclaimed: plain sections or the "In the source only" strip.

**Browser check — must show:**
- **The outcome**, with its three values visibly different (Tone mapping): `verified`, `nothing_to_report`, `could_not_look`. For `could_not_look` the page shows the reason GSD recorded (`target_unreachable` etc.), as a short human sentence plus the raw value in mono. For `nothing_to_report` it shows the reason (`no_criteria`) the same way. Neither is rendered as a pass, and neither shows a green or accent mark.
- **Passed, failed and needs-review counts** as three Heading numerals with squares (zero shown as `0`); on `could_not_look` and `nothing_to_report` the counts read as not applicable ("No criteria were checked.") rather than three zeros, unless the file states zeros and criteria both.
- Each criterion's result with what was observed (failed ones quote what was seen), grouped failed first, then needs review, then passed.
- The target that was checked and when, as text.

**Cross-AI reviews — must show:**
- **Each reviewer**: name, model, and (when the file says) its overall risk. One card or row per reviewer; the reviewers are the unit, not the file's headings.
- **The concerns the reviewers agreed on, first**: a group "Agreed" listing each concern that two or more reviewers raised, with the reviewers named on it and the highest severity among them. Matching reviewers' concerns is a **best-effort text match** (same normalised text, or the same plan reference plus the same first clause); when the page cannot tell, it lists the concern under the reviewer, not as agreed. The page never claims agreement it did not derive.
- **Where they disagreed**: a group "Disagreements" where one reviewer's stance (a concern, a risk level, an approve/revise call) is contradicted by another's, shown side by side with each reviewer named. Disagreements are never merged into a verdict.
- Then each reviewer's full text, collapsed by default, with the summary, strengths, concerns and suggestions as the reviewer wrote them.
- A consensus summary section the writer produced is shown as written, below the derived groups, labelled as the file's own.
- Made-up example (D-11) covers **reviewers who disagree** and a **single-reviewer** file.

### 7. Made-up example rule (VIEW-21; D-10 to D-13)

### 9. Accessibility

- **Headings.** One `h1` per page (`ArtifactHeader`). Panels and sections are `h2`; groups are `h3`. Chips and squares are never headings. The Codebase page's panel switch is **navigation** (links with `aria-current="page"`), not an ARIA tablist; arrow-key tab switching is not added. A "Not mapped" entry is not a link (`data-ghost`, no `button`, no `href`).
- **Copy command.** The button is a real `<button>` with the visible label "Copy command"; its `aria-label` names the command ("Copy command: /gsd-new-project"); the toast is announced through the existing toast region. The command text is selectable and is not inside the button.
- **Could not look vs nothing to report.** Distinguished by icon, word and reason, never colour alone; each outcome chip has an accessible name that includes the reason.
- **Squares and meters.** Squares are `aria-hidden` when a word sits beside them; otherwise `role="img"` with an `aria-label`. A segmented meter has one accessible name ("5 of 12 checklist items done"), its cells `aria-hidden`.
- **Disclosures** (`details`/button) use `aria-expanded`; collapsed reviewer text, template-slot sections and step instructions are reachable by keyboard in document order.
- **Value hiding is accessible too.** "Value not shown" is the visible and spoken text for a withheld variable value; the value is absent from the accessibility tree.
- **Live regions.** None (nothing updates on a timer).
- **Contrast.** Every new text colour is an existing token already validated in both themes; `--muted-foreground` on `--card-veil` (head band) is the weakest pair and is checked in the screenshot review.
- **Narrow widths (390px).** The head, panel list and cards stack; the panel list becomes a column of bars (as Research's spines do under 42rem); the copyable command wraps; no horizontal page scroll; mono paths end-ellipsise with the full value in `title`. Under 42rem the five-tab top bar already wraps to two rows (Phase 9 fix `c93e22f`); a map-only project has fewer tabs, which must not break that rule.
- **`prefers-reduced-motion`.** Nothing animates; nothing to disable.
