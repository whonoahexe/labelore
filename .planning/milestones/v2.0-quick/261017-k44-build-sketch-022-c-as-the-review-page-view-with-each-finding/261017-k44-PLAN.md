<objective>
Build sketch 022's winner, **C: Review threads** (with its round-2 fold control), as the REVIEW page view, with each finding's fix outcome taken from the matching REVIEW-FIX file. A REVIEW.md is the code reviewer's findings for a phase or quick task. Today it renders through the generic promoted-section view (Summary, Critical Issues, Warnings, Info, a facts block), which never says what is still in the code and never shows what the fix run did. The new page answers, in order: what is still in the code and how bad (the verdict, the tally, the reviewer's summary), where each problem sits and what the reviewer suggested (file-grouped threads, worst first), what happened to each finding (a reply: fixed with its commit, skipped with the reason, not attempted, or no reply yet), and what it leaves to Source (Also in this report).

Purpose: REVIEW is the next type in the per-type view loop (DISCUSSION-LOG, CONTEXT, RESEARCH, PATTERNS, UI-SPEC, UAT, VALIDATION, SECURITY, UI-REVIEW, PLAN, SUMMARY and VERIFICATION are built). It must degrade, never throw, across the shapes the sketch proved (frontmatter-resolved, a partial fix report, an all-fixed fix report, 26 open findings, a small review, a clean review) plus the harder real shapes found at planning time (combined fix headings, flat count frontmatter, a `blockers_resolved` string, an empty narrative container).

Output: two extractors and two handlers on the server, a server-side join of the sibling REVIEW-FIX into the review's document response, a pure composer, the view components and one delimited CSS block wired through the view-registry seam; nine verbatim fixtures; extractor, handler, join, composer, corpus and contract tests; an e2e spec; the design-language bullet; and Playwright side-by-side evidence against the sketch.
</objective>
