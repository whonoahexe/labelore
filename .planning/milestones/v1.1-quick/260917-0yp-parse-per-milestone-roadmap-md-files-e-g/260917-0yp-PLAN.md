# Quick 260917-0yp: Parse per-milestone ROADMAP.md files for archived phases

<objective>
Make `.planning/milestones/vX.Y-ROADMAP.md` a real, parsed roadmap source so archived phases show the goal, depends-on, requirements, success criteria and plan descriptions GSD actually recorded for them — instead of the nulls and empty arrays they show today when the root ROADMAP.md compacted that milestone's `<details>` block down to a bare checklist and a "Full detail:" link.

Purpose: GSD's `/gsd-complete-milestone` moves a milestone's rich phase detail out of the root file and into a per-milestone snapshot. Labelore's discovery layer already classifies that snapshot correctly (`location: 'milestone-root'`, `kind: 'roadmap'`, `milestoneVersion` parsed) — nothing downstream ever reads it, so every archived phase in such a project renders hollow.

Output: one widened handler match, one per-milestone phase-block source threaded into assembly, one ordered source list in the presentation layer, test coverage for the new path and for the unchanged-when-absent path, and a regenerated dense golden.

Task-local requirement IDs:
- 0YP-01: per-milestone ROADMAP files parse through RoadmapHandler into flat `structured.phases`.
- 0YP-02: archived phases source name/goal/depends-on/requirements/success-criteria from that file, with field-level fallback to the root block.
- 0YP-03: archived plan descriptions and formal plan progress source from whichever roadmap actually carries plan entries, per-milestone preferred; root roadmap looked up by canonical path.
- 0YP-04: strictly additive — absent, empty or malformed per-milestone files change nothing and never throw.
</objective>

<assumption_delta_decision>
**Transition:** singular → plural. Until now there has been exactly ONE source of roadmap phase blocks (`.planning/ROADMAP.md` — its top-level `### Phase N:` headings for the live milestone, its `<details>` groups for archived ones). This task introduces a SECOND source for archived milestones only: `.planning/milestones/vX.Y-ROADMAP.md`.

**Noun that becomes primary:** the per-milestone `vX.Y-ROADMAP.md` phase block, **for archived phases of that version only**. The live milestone's source is untouched and stays the root file, exclusively.

**Call: PROMOTE, with field-level fallback (not whole-block replace, not add-alongside).**

- Per-milestone block wins per field when it supplies a value (non-null for `goal`/`dependsOnRaw`, non-empty for `name`/`requirementIds`/`successCriteria`/`plans`).
- The root `<details>` block fills every field the per-milestone block leaves empty, and remains the sole source when no per-milestone file exists for that version.
- `roadmapComplete` is never merged across sources — it is taken from whichever block supplied the `plans` array it describes, because it is a derived summary of exactly that array and mixing the two would assert a completion state about a checklist that was never read.

**Rationale:** whole-block replace would let a per-milestone file that omits a plan checklist silently delete plan rows the root file still carries — a regression for a real GSD shape. Add-alongside (surfacing both) would force every downstream renderer to learn a two-source concept for a field that has exactly one correct value. Field-level promotion is the only option where a project with no per-milestone file produces byte-identical output to today, which is what this project's CLAUDE.md "Compatibility" constraint (*GSD's artifact set evolves, so unknown files must degrade rather than break*) asks for: the new source is purely additive headroom, never a new failure mode.

**Recorded consequence to watch:** `src/server/project-presentation.ts`'s `roadmapPhaseRecord()` currently finds the root roadmap with `Object.values(project.artifacts).find(a => a.kind === 'roadmap')`, which only resolves correctly because insertion order puts `location: 'root'` before `location: 'milestone-root'`. Per-milestone files already carry `kind: 'roadmap'`; once they also carry structured phases, that accidental ordering becomes load-bearing. Task 2 anchors the lookup to the canonical `.planning/ROADMAP.md` path as part of this decision, not as unrelated cleanup.
</assumption_delta_decision>
