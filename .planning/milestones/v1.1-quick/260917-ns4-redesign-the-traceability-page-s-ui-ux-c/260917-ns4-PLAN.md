<objective>
Redesign /traceability so its coverage story is legible at a glance instead of row by row: an
at-a-glance summary strip that also hosts the filter controls, three-way proportional coverage bars
at page and category level, a hierarchical row layout in place of the flat ruled grid, and the
non-active requirement tiers folded into the roadmap page's existing collapsible history treatment.

Purpose: the page currently answers "what does each requirement say" but not "how are we doing" —
the user's three named complaints are that plain tables feel flat, there is no sense of proportion,
and the filter bar feels bolted on. Each is addressed structurally, not cosmetically.

Output: a redesigned traceability page, an extended (still pure) projection feeding it, and a new
source-level contract test pinning the redesign.
</objective>

## Resolved: tier → milestone mapping (CONTEXT "Claude's Discretion", item 1)

CONTEXT flagged this as open and named the fallback. Investigated at plan time; resolved as follows.

**Finding:** grouping the History section by milestone is not fuzzy — it is impossible from the data
the page receives, and the fallback CONTEXT pre-authorised is the correct design.

Evidence:

1. `RequirementsHandler.match` (src/planning-repo/handlers/requirements.ts) accepts only
   `ref.location === 'root'` with basename `REQUIREMENTS.md`. The archived per-milestone corpora
   that exist on disk — this repo has `.planning/milestones/v1.0-REQUIREMENTS.md` — are never
   parsed, so no archived-milestone requirement ever reaches `presentation.requirements`, and
   therefore never reaches `TraceabilityViewModel`.
2. `tierOf()` normalises only `v1`/`v2`/`future` and otherwise returns the section heading verbatim.
   `fixtures/dense` consequently carries the tier strings `v3.0 Requirements` and
   `v4.0 Requirements` — free-form headings, not milestone versions.
3. `buildTraceabilityViewModel` already splits the corpus on checkbox presence, not on tier
   string: `groups` holds the one actionable tier, `deferredRows` holds every non-actionable tier.

**Decision:** the History section groups by **tier string alone** — exactly CONTEXT's stated
fallback. Its content is the existing `deferredRows`, regrouped by `row.tier`. No milestone
dimension is invented, and no archived-corpus parsing is added (that would be a planning-repo change
well outside a UI/UX redesign).

**Naming consequence:** the non-active tiers here are *deferred/future*, not *past*. The section
reuses the `.history-section` / `.history-milestone` / `.history-tree` **visual treatment** verbatim,
as CONTEXT specifies, but keeps deferral-accurate copy. The existing `Deferred requirements` heading
survives as the section heading; each disclosure is labelled by its tier string. The toggle is
labelled for what it actually does rather than borrowing the roadmap's archival vocabulary.
</discretion_resolution>

**test/token-guard.test.ts** — scans globals.css outside `:root`/`.dark`/`@theme inline`:
- every padding/margin/gap/inset/top/right/bottom/left value must be a whole `var(--space-*)` call,
  or `0`, or `auto`, or a percentage. A raw rem/px/em anywhere (including inside `calc()`) fails.
- `font-size`, `line-height`, `letter-spacing`, `font-weight`, `font-family` must each be a single
  whole `var(...)` call. A usage-site `clamp()` fails.

- a `color-mix(...)` written at a usage site fails if it appears **twice** anywhere in usage
  position, or if it duplicates an existing token's own value. Recurring recipes must become a
  named `:root` token.
