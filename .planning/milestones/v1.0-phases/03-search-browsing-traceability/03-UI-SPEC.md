# Phase 3 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Read this contract as extension, not replacement.** Phase 2 shipped a complete, hand-authored
design system (custom BEM-ish CSS classes over Tailwind v4 tokens, `@base-ui/react` headless
primitives, no shadcn CLI-generated components). Phase 3 adds four new surfaces — a header search
field, a search results page, a persistent tree sidebar, and a traceability table — and every one
of them is specified here in terms of classes, tokens, and patterns that already exist in
`src/web/styles/globals.css` and `src/web/components/`. Where a genuinely new primitive is needed
(the search input, the sidebar track) it is named explicitly as new and grounded in the nearest
existing analog.

## Spacing Scale

The codebase does not run a rigid 4px design-token grid; it runs a fluid rem-based system —
fixed rem paddings for chrome, `clamp()` for content gutters that need to breathe at wide
viewports. The values below are the **actual values already in production use**, mapped to their
px equivalents (16px root) and organized by role so Phase 3 reuses rather than reinvents.

| Token | Value | Usage (existing citation) |
|-------|-------|----------------------------|
| xs | 4px (`0.25rem`–`0.4rem`) | Icon-to-text gaps inside chips/labels — `.status-chip { gap: 0.4rem }`, `.section-heading.compact > span` |
| sm | 8px (`0.5rem`) | Compact list-item gaps — `.attention-list`, `.criteria-list` |
| chip-pad | ~9–10px (`0.55rem`–`0.65rem`) | Chip/badge internal padding — `.status-chip { padding: 0.38rem 0.55rem }`. **Exception to the 4px grid, already established — reuse verbatim, do not round to 8/16.** |
| md | 16px (`1rem`) | Default element spacing, card body padding — `.dashboard-loading`, `.progress-panel > header` |
| lg | 24px (`1.5rem`) | Section-internal gaps — `.milestone-flow, .history-section { gap: 1.5rem 2rem }` |
| xl | 32px (`2rem`) | Major inter-section gaps — `.page-stack > * + *` rhythm via `.dashboard-grid`/`.wave-stack` |
| section-pad | `clamp(1.25rem, 3vw, 2rem)` | Card/panel padding that scales with viewport — `.progress-panel`, `.attention-panel`, `.preview-panel` |
| page-pad | `clamp(2rem, 5vw, 5.5rem) clamp(1rem, 4vw, 3.5rem) 7rem` | `.page-stack` outer padding — reuse unchanged for `/search` and the traceability route |

Exceptions: the `0.6rem`–`0.85rem` family used across eyebrows, status chips, and micro-labels is
a typographic micro-scale (see Typography), not a layout-spacing step — do not treat those numbers
as spacing tokens even though some coincide with the px values above.

**New for Phase 3 — sidebar track.** D-09 activates the previously-unused `--sidebar` oklch tokens
in a new persistent left column. Base the track width on the existing `.document-outline` sidebar
precedent (`grid-template-columns: minmax(10rem, 14rem) minmax(0, 1fr)`) rather than inventing a
new width: `minmax(14rem, 18rem)` for the tree (wider than the in-page outline because it carries
deeper nesting — phase → plan/artifact — not just heading depth), sticky at `top: 0` under the
`z-index: 20` header, `height: calc(100vh - <shell-header rendered height>)`. Measure the header's
actual rendered height (it is not a fixed rem value today — `.shell-header` sizes to its padded
content) rather than guessing a number; the `.document-outline`'s `top: 5.5rem` is a *content-area*
offset (inside `.page-stack`'s own top padding) and is not directly reusable for a shell-level
sidebar sitting flush against the sticky header.

## Typography

Three roles are relevant to Phase 3's four new surfaces; the existing Display scale
(`clamp(2.6rem, 7vw, 5.6rem)`, dashboard hero only) is out of scope here.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 13px (`0.82rem`) | 400 (`--font-sans`, Space Grotesk) | 1.55 |
| Label / eyebrow | 11px (`0.67rem`), uppercase, `letter-spacing: 0.08em` | 600 (`--font-heading`, JetBrains Mono) | 1.3 |
| Heading (section h2/h3) | 21px (`1.3rem`, matches `.progress-panel > header h2`) | 600 (`--font-heading`) | ~1.2 |
| Display | N/A for Phase 3 | — | — |

Applied to the four new surfaces:

- **Search input text** (typed query): Body — 13px/400/1.55, matches every other prose/UI text.
- **Result title / requirement ID**: 0.84rem semibold, matching `.metadata-panel h2` / `.requirement-list strong` — bold enough to scan without introducing a fifth size.
- **Snippet body text**: Body — 13px/400/1.55, identical treatment to `.attention-list p`.
- **Group labels** (search result phase/type groups; tree top-level groups; traceability category headers): Label/eyebrow — 11px/600/uppercase, identical to `.eyebrow` / `.status-chip`. This is the single strongest existing signal for "this text organizes other text," and Phase 3's grouping (D-07, D-14) is exactly that job.
- **Match count / chip copy** ("3 matches", "Status mismatch", "Uncovered"): reuse `.status-chip` verbatim (0.64rem/600/uppercase inside a bordered pill), never invent a new chip style.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA | "See all N results" — dropdown-to-`/search` transition link (the one net-new user-facing action this phase adds; every other interaction is navigation into content that already has its own established copy, e.g. `Popover`'s existing "Open"). |
| Placeholder (header search field, nothing typed) | `Search` — minimal, matching the app's icon-plus-field chrome convention. No dropdown renders until a query is typed. |
| Error state (search endpoint failure) | `Search is unavailable.` — rendered as a single `.notice.destructive` row at reduced scale *inside* the dropdown, so the message appears at the field the user is typing in. Distinct from the `Indexing…` transient (D-04), which is not an error. |
| Empty state heading (search results, zero matches) | `No matches for "{query}".` |
| Empty state body (search results, zero matches) | `Nothing in .planning/ contains that exact token or its prefix. Search does not correct typos or match approximately — check the spelling and try again.` (Grounds the empty state in D-05's deliberate no-fuzzy-matching decision so it reads as a design choice, not a bug.) |
| Empty state heading (dropdown, zero matches, index ready) | `No matches` (compact — dropdown has no room for a full sentence) |
| Transient state (index still building) | `Indexing…` — with helper text `Results will appear automatically once the index finishes.` per D-04: never a disabled input, never a dropped query. |
| Empty state (tree navigator, a location has no files — e.g. no `quick/` directory) | `Nothing here yet.` — mirrors the existing `.empty-note`/`.empty-flow` tone (`"No archived milestones are present in this snapshot."`) rather than inventing a new voice. |
| Empty state (traceability, uncovered requirement) | Chip label `Uncovered` on the row; no separate empty-state copy needed since D-15 renders it as a marked row, not a blank section. |
| Error state (search results page) | Heading `Search could not be loaded.` / body `{error.message}` — exact structural mirror of `roadmap-page.tsx`'s existing `The roadmap could not be loaded.` / `{roadmap.error.message}` pattern inside `.notice.destructive`. |
| Error state (traceability view) | Heading `The traceability view could not be loaded.` / body `{error.message}` — same `.notice.destructive` pattern. |
| Error state (tree navigator) | No separate error copy — the tree renders from the same `presentation` query the shell already fetches; a fetch failure is already surfaced once by the existing `.shell-notice` ("The shell could not refresh its snapshot metadata...") and the sidebar simply does not render, consistent with how the rest of the shell degrades today. |
| Status mismatch flag (traceability) | Chip label `Status mismatch` next to the two disagreeing values, e.g. `Requirement: Complete` / `Phase: In progress` — both signals always shown side by side per D-13, never collapsed into the flag alone. |
| Destructive confirmation | None — Phase 3 is read-only (PROJECT.md's access constraint). No delete, write, or state-mutating action exists anywhere in this phase's scope. |
