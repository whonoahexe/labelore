<objective>
Show every requirement beside the phase covering it, with both status signals intact.

Purpose: The most valuable row this view can show is a requirement nothing covers; the second most
valuable is one whose two status signals disagree. Merging those signals into a single verdict would
destroy exactly the information the view exists to surface — this extends Phase 2's D-02 rather than
inventing a new rule.
Output: A server-side traceability projection joining requirements to their covering phases' own
state, and a filterable, category-grouped view at its own top-level route.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| REQUIREMENTS.md text → rendered table cell | Corpus-derived requirement text, ids and category headings are placed into the DOM |
| dangling reference raw text → rendered marker | Unresolved reference text of arbitrary shape is rendered beside a marker |
| filter input → row predicate | User-typed text drives a matching pass over every row |

## STRIDE Threat Register (OWASP ASVS L1; unresolved high severity blocks completion)

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-04-01 | Tampering | traceability table cell rendering | high | mitigate | Requirement text, ids, category headings and dangling raw references render as escaped React text nodes; React's raw-HTML injection prop is asserted absent from the page by source grep. |
| T-03-04-02 | Tampering | covering-phase link targets | high | mitigate | A covering phase renders as a link only when it resolved, and its href comes from the route builder the presentation already produced; an unresolved reference renders as text and never as a link, so no raw corpus string can become a navigation target. |
| T-03-04-03 | Denial of service | filter predicate | medium | mitigate | The predicate uses case-insensitive substring comparison over a bounded row set, never a regular expression constructed from user input. |
| T-03-04-04 | Repudiation | merged status verdict | high | mitigate | The two status signals travel as separate fields end to end and a source grep asserts no merged-status field exists — a view that silently reconciles a disagreement is exactly the failure this requirement exists to prevent. |
| T-03-04-05 | Information disclosure | requirement text | low | accept | The view echoes the user's own local requirements document back to the same user on localhost. |
</threat_model>
