# Quick 261017-k44: the REVIEW page with each finding's fix outcome

A REVIEW page now opens on how many findings are still in the code and how bad they are, then lists every
finding grouped by the file it sits in (worst first), and shows what happened to each one from the matching
REVIEW-FIX file: fixed with its commit, skipped with the reason, not attempted, or no reply yet.

The measured commit range from the start of this item is 4 because it includes `ea845af` (the user's
Playwright per-test limit change, made while this item was paused). The item's own commits are three:
`c931ace` (Task 1), `eae91ea` (Task 2) and `a790a28` (Task 3).

## What the page shows

- **Head and hero.** An eyebrow ("Code review · Phase N", or "Quick code review · id"), the reviewed date, the
  warning chip, copy path and View/Source, then the only h1 (the ROADMAP phase name, else the review's own
  title). Under it: the verdict sentence ("4 of 10 fixed. 6 still in the code."), the sub line, the facts
  (Files, Depth, fix run or "Resolved"), a four-cell tally, and the reviewer's first summary paragraph as a
  pull quote with a "Full summary" link that opens Source at the Summary heading.
- **Review threads.** One block per file with a line ruler of where its findings sit, an "Outside scope" chip
  where the declared file list does not name the file, and the count. Each finding shows its line gutter,
  severity and ID, title, outcome stamp, the problem, a "Suggested change" block, any other labelled field, and
  a reply with the outcome. Fixed findings fold into one-line rows; a row unfolds its thread, an unfolded fixed
  thread has "Fold −", and "Show fixed threads (N)" unfolds them all (switching it resets every thread).
- **Back matter.** Files reviewed with no finding as quiet chips (14, then "+N more" / "Fewer"), one "Also in
  this report" chip row (the fix report as a link to its own page, the files list, other sections that open
  Source at their heading, Frontmatter) and a footer with the reviewer and depth. A clean review reads
  "Clean. Nothing to fix across N files."

## Decisions as built

- Own head with an early return in View mode (the SUMMARY page precedent); Source mode is the plain page, and a
  payload without parsed findings still gets the existing promoted-section view.
- Outcomes are joined on the server, so the verdict never flashes "none fixed". Only the sibling path (the
  review path with `-REVIEW.md` swapped for `-REVIEW-FIX.md`, matched exactly) counts; the REVIEW-FIX's
  `review_path` frontmatter is ignored.
- Outcome order per finding: the fix report, then the review's own `resolved:`, then `blockers_resolved`, then
  an inline RESOLVED note; a finding the fix report never names is open (critical, warning) or not attempted
  (info).
- Findings group by their first file, merging refs with the same path (so sideby IN-02 shows no "+1 file").
- The page adds no motion; hover is a colour change only. Every colour is a theme token or a design-language
  tone, and the parse-degradation tones never colour content.
- Task 3 added one breakpoint-scoped rule: under 42rem the tally goes to two columns (borders adjusted). No
  other breakpoint was added.
- `docs/design-language.md` records the page's tone and accent uses in one new bullet; no vocabulary row.
