<objective>
Build sketch 027's winner, **C: Lifecycle**, as the page view for GSD todo files (`.planning/todos/pending/`, `.planning/todos/completed/`, `.planning/todos/done/`). The page shows one todo as a journey. A strip runs Noted → Captured → Closed (or Now while it is open) above one numbered spine. The spine holds the notes the todo came from, then the todo itself (the problem beside the solution, the files, the other sections folded), then how it was closed, or a dashed "still open N days". Today these files are discovered as an unrecognised kind, parsed by the generic handler and drawn by the fallback view. Their notes are never shown with them.

Purpose: todos are the next type in the per-type view loop, and the first one whose page needs another file. A todo's source notes live in `.planning/notes/`, linked by frontmatter `notes:`, `[[slug]]` links, `notes/…md` mentions or word-for-word promotion. GSD writes todos in three shapes: add-todo (Problem / Solution / Resolution), note promote (Goal / Context / Acceptance Criteria) and hand-written prose with checklists and a closing callout. All three must read, and unknown shapes must degrade, never throw. The todo↔note relation is built once, server-side and in both directions. The sibling NOTE page item in this batch (261023-61l, "the todo it became") then consumes the same module instead of writing a second one.

Output: directory-position kind routing; a server-side extractor and handler; the shared todo↔note relation and the TODO page's server join; a pure composer, the view components and one delimited CSS block, wired through the view-registry seam; fifteen verbatim fixture files; extractor, handler, relation, composer, corpus and contract tests; a fixture-server helper and an e2e spec; the design-language record (including the dashboard's matching severity colours); and a Playwright side-by-side against the sketch.
</objective>
